**治理路线保留，但第一刀缩小为：补完整已有的会话消息存储模块。**

上一版把会话列表、草稿、保存、请求运行和界面连接放在第一批，实际上跨越了几个不同的生命周期。详细追踪后，不适合同时改。先完成一个真实模块的状态与操作归属，然后再处理会话长期状态和单次请求。

## 2. 第一刀到底做什么

### 2.1 使用已有对象，补齐它的实现

已有消息保存对象 `StudySessionMessagePersistence` 保留名称，单独放入同名源文件。它负责：

- 消息文件的定位、读取和编码。
- 已加载编号与上次成功写入内容的维护。
- 根据当前会话数据，计算需要写入、删除的消息文件。
- 工作区提交成功后，确认本次写入结果。
- 归入这块职责的现有消息导入与文件恢复操作。

工作区总管继续负责：

- 当前会话选择，以及课程、资料和会话之间的协调。
- 把加载结果应用到会话集合。
- 恢复上次中断回答的会话状态，更新对应的全局启动提示。
- 统一调度保存、判断结果是否属于当前保存代次，以及展示已有错误状态。

消息模块只接收所需数据和现有存储地址，不持有总管，不读取界面状态。目录和编码方式复用现有消息文件支持代码；具体文件写入仍由已有文件工作对象完成。

首刀不会把历史、草稿和运行任务一起塞入消息模块。这个模块管理的是消息文件及保存基线，不是整个 Chat 产品。

### 2.2 保留三处容易搬错的语义

1. **未加载不等于空。** 尚未加载的历史会话不能被当成空正文写回。读取并应用消息后，登记的是当前处理后的会话内容；新建会话和课程恢复带来的内存消息仍按原入口标记。
2. **准备写入不等于保存成功。** 计算待写数据时只形成请求；文件工作对象完成整批提交、总管确认结果后，才更新上次成功写入内容。失败后相同内容仍必须进入下一次保存。
3. **保留已有保存调度。** 消息文件继续与工作区快照共同提交，不新建线程、锁、事务协调器、自动重试层或备用写入路线。

这些是当前代码已有的行为。本次把对应数据和操作放到同一处，不再为它们增加一套防御机制。

### 2.3 预计四个文件

| 文件职责 | 具体改动 |
| --- | --- |
| 新的消息存储源文件 `Sources/WeiBei/Stores/StudySessionMessagePersistence.swift` | 移入已有类及其读取、编码、差异计算、缓存确认操作；转移已有相关类型 |
| 消息与工作区的连接文件 `Sources/WeiBei/Stores/WorkspaceStore+SessionMessages.swift` | 保留选择哪些会话要加载、应用结果及错误展示；移除已归入模块的重复实现 |
| 工作区总管 `Sources/WeiBei/Stores/WorkspaceStore.swift` | 初始化消息模块，将准备消息写入和成功确认接到它；保存顺序及结果判断留在原位置 |
| 现有消息保存测试 `Tests/WeiBeiSafetyTests/SessionMessageExternalizationTests.swift` | 复用现有六例，补齐下面说明的一条行为缺口 |

启动清理、课程恢复、全局搜索和记录页的调用均已追踪。它们使用的现有加载入口保持语义；实施时核对接线，不顺手改写这些业务。

## 3. 测试收敛到真正需要的部分

### 第一刀复用现有六例

现有消息保存测试已经直接覆盖：

| 用户结果 | 现有检查 |
| --- | --- |
| 原有聊天载入后消息不丢 | 旧工作区消息导入 |
| 重开不会重复搬移、覆盖原备份 | 第二次启动 |
| 导入校验失败仍保住正文 | 失败导入 |
| 一个会话文件损坏不影响其他会话 | 损坏文件读取 |
| 保存甲会话不重写乙会话 | 单会话增量保存 |
| 重开后未点开的会话仍有正确数量，加载后正文在 | 延迟加载 |

这些都是现有测试，不为本次重构再复制一遍，也不要求把它们全部改成直接实例化小模块的单元测试。它们经过真实总管和临时目录，能验证完整连接是否保持。

### 只补一个已定位的缺口

在现有测试及相关保存失败检查中，**未找到“正常聊天保存失败 → 重试 → 读回同一消息文件确认新增正文”这一完整闭环**。现有失败检查主要验证导入、笔记或课程状态，不能直接替代它。

在原消息保存测试文件补一个案例：

> 已有聊天追加一句话，工作区保存被现有写入注入入口触发失败；恢复写入后重试，从真实消息文件读回这句话。

它保护的就是“保存失败不能把消息缓存提前记成已保存”。复用已有临时目录和工作区写入注入入口，检查实际文件内容；不检查缓存私有字段、函数名或源码词语。实施前若最新主线已包含同一行为检查，直接复用。

### 验证节奏

第一刀本地编译后，只运行消息保存这一组检查；完成后使用仓库已有的合并检查。后台保存、其他模块的现有检查照常保留在原检查流程中。

```sh

```

这些是实施时要运行的命令，本次研究未执行它们。

第一刀保持执行时机、观察方式和渲染代码，所以不另开全应用截图、主题尺寸矩阵或滚动性能项目。后续实际修改输入观察、消息刷新和渲染连接时，再对受影响的真实交互做改前改后对照。测试失败先查具体原因，不盲目加断言、重试或保护分支。

## 4. 后续如何把总管真正拆下来

| 顺序 | 状态与操作归属 | 具体接入要求 | 对应验证 |
| --- | --- | --- | --- |
| 1 | 消息文件与保存基线 | 按上述四文件方案完成 | 现有六例，加一条正常失败后重试 |
| 2 | 会话集合、当前会话与按会话编号保存的草稿 | 把查询、切换、增删、课程关联和快照恢复的修改入口一起收拢；输入框保留本地编辑缓冲 | 复用草稿隔离、继续上次工作、会话标题和历史保存检查 |
| 3 | 本次 Agent 请求的任务、进度、停止与结束 | 扩充已有运行对象的行为；保留请求捕获的会话编号及消息编号，不把结果写向切换后的当前会话；笔记和课程操作仍调用相应模块 | 复用并行会话、停止与退出、流式显示检查 |
| 4 | 笔记草稿、编辑快照、写入与恢复 | 沿已有编辑会话、恢复点和唯一写入闸门收口；让编辑器、Agent 写笔记和重命名都使用同一套保存规则 | 复用笔记写入闸门、正文事故和 Agent 动作真实落盘检查 |
| 5 | 课程、资料归属、文件对账和课程状态 | 接管课程集合与维护任务，沿用独立文件工作对象；笔记正文交给笔记模块，跨模块操作由工作区协调 | 复用课程导入／移除、外部变更、瞬断与保存检查 |
| 6 | 笔记、会话、选区浮窗各自的界面 | 在对应业务模块稳定后按已有视图拆分；叶子视图只获取实际用到的状态和操作 | 受影响入口的轻量真实操作；观察链变化才做相应性能对照 |

第二步以后按真实调用面分批落地，不预先固定“一批几百行”或日历工期。任何一批都不能只移动字段，然后继续让其他模块随意修改其内部数组和字典。

最终工作区总管保留组装、导航、跨模块操作与全局恢复／保存协调。治理效果体现为：改会话消息主要改会话模块，改笔记保存主要改笔记模块。首刀只完成保存职责独立，不宣称已经解决整个上帝类或获得性能提升。

## 5. 哪些设计明确不引入

| 做法 | 本次判断 |
| --- | --- |
| 只有一个实现的协议、工厂或依赖注入容器 | 具体类型和已有参数足够 |
| 新事件总线、通用仓库层、可配置的“治理框架” | 当前没有需要它们解决的问题 |
| 同时更换数据观察机制、存储格式或并发模型 | 会把职责迁移和行为变化混在一起，分开处理 |
| 自动重试、额外兜底路径、复制一套旧实现随时切回 | 沿用当前有效机制，修复确定的问题 |
| 为每个函数加测试、检查源码必须含某个词、设文件行数门槛 | 检查用户行为、真实数据和必要连接 |
| 为证明“可单测”重写所有测试夹具、增加虚拟文件系统 | 现有临时目录与注入入口已能验证 |

当前实际防止正文丢失的校验、写入顺序与错误处理继续有效；治理过程中不因它们“看起来防御性”就删除。已被完整替代的重复实现直接移除，不建立兼容包装。

现有项目规则已经要求只改必要调用路径、避免无依据抽象与测试；本次不新增全局规则、项目规则或 CI 配置。
