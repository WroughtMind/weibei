## 结论

本次只修三个已经定位的问题：重开会话后旧消息难以出现、会话窗格开合明显卡顿、空白页上方出现白色短竖线。全部放在同一个合并请求内，以最小根因修复完成，不回退 Fable 已交付的流式输出、富文本渲染、公式、表格、代码块、输入框和现有窗格动画。

Codex 负责把代码做扎实并完成必要的工程检查；肠粉负责最终真实体验验收。自动验证只守住明确的回归和性能门槛，不用大量时间替代人的体感判断。

## 已证实的问题与根因

| 问题 | 已证实根因 | 修复方向 |
| --- | --- | --- |
| 重开会话后向上滑，只容易看到最近一批消息 | 消息没有丢失；会话视图默认只展示最近 30 条。现有滚动探针只知道“离底部多远”，到达顶部时不会触发现成的“展开更早消息”能力 | 让滚动探针同时报告顶部位置；用户真实上滑到顶时自动展开一页，并恢复原来的阅读锚点；保留顶部按钮作为兜底 |
| 会话窗格开合远慢于文稿、笔记窗格 | 外层窗格动画每一帧都改变会话内容宽度；最近 30 条消息中的富文本网页视图随之反复测宽、解冻高度和回传尺寸，造成主线程连续重排 | 只在窗格结构切换的短动画期间固定会话内部阅读宽度，让外层继续原有动画和裁切；动画结束后一次性提交最终宽度 |
| 空白页中间靠上有白色短竖线 | 空白页组件主动绘制了一条居中的 1 像素装饰矩形，并非输入光标或系统分隔线 | 删除这条装饰，不改空白页其他层次、分隔线或背景 |

## 用户结果

1. 用户重新进入一个长会话后，持续向上滑可以自然看到更早内容，不需要反复碰运气或寻找小按钮。
2. 展开更早消息时，当前阅读位置不会突然跳走；顶部按钮仍可手动使用。
3. 文稿、笔记、会话三个窗格的打开和收回恢复到同一档的顺滑感。
4. 会话窗格动画期间不反复重排整段富回答；动画结束后内容宽度、排版和点击区域正确。
5. 流式文字、Markdown、公式、表格、列表、代码块、消息操作和输入框行为保持现状。
6. 全部内容窗格关闭时，空白页不再出现白色短竖线。

## 不可回退清单

- 不关闭或降级 Milkdown、KaTeX 和富回答网页渲染。
- 不把公式、表格、列表或代码块改成能力更弱的原生纯文本展示。
- 不取消流式前缀、打字机效果、流式高度保护或消息最终态切换。
- 不取消最近 30 条的首屏控制，也不一次性挂载全部历史消息。
- 不替换现有 AppKit 窗格动画，不通过缩短到近乎无动画来伪造顺滑。
- 不改会话持久化格式、协议、Agent 输入框和无关视觉。

## 实现方案

### 一、历史消息自然加载

复用现有的分页窗口、展开动作和锚点恢复能力，只补齐触发链路：

1. 滚动探针报告“离顶部”和“离底部”的距离。
2. 仅当用户已经完成初始定位、正在向上浏览并真正到达顶部阈值时，自动展开一页更早消息。
3. 加入一次展开的重入保护，避免一次滚动连续加载多页。
4. 展开后恢复原顶部消息的视觉位置，防止内容跳动。
5. 保留“查看更早消息”按钮，作为辅助功能和异常情况下的手动兜底。

这部分不改存储层，因为当前证据已经确认历史消息存在，故障发生在展示触发层。

### 二、会话窗格开合性能

不重写消息列表，也不动富文本协议；先在现有宽度测量链路上消除动画帧级抖动：

1. 识别“打开或关闭某个内容窗格”这一段结构切换动画。
2. 动画进行时固定会话内部阅读列宽，外层窗格仍按现有 0.24 秒动画移动和裁切。
3. 动画结束后只提交一次最终测量宽度，让可见富文本消息完成一次必要重排。
4. 普通拖动分隔条和调整窗口大小仍保持实时响应，不被永久锁宽。
5. 流式生成期间沿用当前高度冻结和最终态交接逻辑，不引入第二套状态机。

若这一级修复未达到性能门槛，停止扩大改动并提交测量证据；在肠粉确认前，不进入稳定文稿工作区等共享核心模块做第二层改造。

### 三、空白页白线

只删除空白页中央的装饰矩形。它没有交互和状态职责，不增加条件开关，也不为它建立新抽象。

## 计划改动边界

| 区域 | 计划动作 | 边界 |
| --- | --- | --- |
| 会话展示模块 | 补顶部探测、自动展开保护、动画期间阅读宽度稳定 | 不改存储、消息协议和 Markdown 渲染能力 |
| 空白工作区模块 | 删除白色竖线装饰 | 不改其他空白页布局 |
| 自检模块 | 增加最小回归检查 | 只检查本次三个契约，不扩建测试框架 |
| 工作区状态模块 | 仅在代表性性能场景需要丰富历史夹具时占用 | 不改变生产业务逻辑 |

共享文件计划占用：`Sources/WeiBei/Stores/WorkspaceStore.swift` 仅允许用于代表性验收夹具，`Sources/WeiBeiSelfCheck/main.swift` 仅允许用于最小回归检查；释放条件是工程验证通过并更新草稿合并请求。第一轮生产修复不占用 `StableDocumentWorkspace.swift`。

## Codex 负责的工程验证

只做能证明代码正确的最小闭环：

1. 发布配置编译通过。
2. 现有自检与网页编辑器检查通过。
3. 用一个 30 条交替消息、包含标题、列表、表格、代码和行内／块级公式的代表性场景，分别测一次修复前和修复后。
4. 历史自动展开检查：首次定位不误触发、到顶只展开一页、原阅读锚点不跳、按钮仍可用。
5. 窗格性能检查：结构切换期间不逐帧向富文本消息广播新宽度；同机代表性场景最大主线程停顿目标低于 50 毫秒，会话窗格开合耗时不超过文稿／笔记窗格的 1.5 倍。
6. 空白页检查：目标装饰已移除，其他分隔线契约仍在。
7. 分支已推送、草稿合并请求写清验证结果、工作树干净。

这里不做长时间反复点按、全视觉穷举或替肠粉决定“够不够丝滑”。性能门槛若一次代表性复测未过，直接回到根因，不用微调动画数字粉饰结果。

## 肠粉负责的真实 App 验收

代码和工程检查完成后，Codex 提供可运行版本，肠粉只需按真实使用习惯验收：

1. 打开一个超过 30 条消息的旧会话，重新进入后向上滑，确认更早消息自然出现且阅读位置不跳。
2. 在富回答已经较多的情况下，连续打开／关闭文稿、笔记和会话窗格，确认会话窗格已经恢复到可接受的丝滑程度。
3. 发起一次包含流式文字、公式、表格和代码块的回答，确认现有新效果没有退化。
4. 关闭全部内容窗格，确认空白页白色短竖线消失；浅色和深色外观各看一次。
5. 顺手拖动分隔条和调整窗口大小，确认实时布局没有被锁死。

通过时只需明确说“验收通过”；未通过时指出上述编号和现场表现即可，不要求先录制完整视频。
