# 魏碑会话原生流式 Markdown 计划

日期：2026-08-30  
状态：实现完成；最终流式 Markdown 固定提交的完整全新匿名拉取因公开网络 sideband 断连，待组合分支复核；候选 App 待真实验收  
范围：魏碑会话中的模型回答渲染

> 一句话定案：**借用微软 SwiftStreamingMarkdown 的原生流式 Markdown 骨架；公式准确性由魏碑的小型固定分支修正并接入 SwiftMath；写作编辑和资料阅读仍走现有路径。**

## 一、结论与产品边界

1. 本计划只改魏碑“会话里的模型回答”渲染，目标是把普通回答从每条一个 `WKWebView` 小网页，改为 SwiftUI/AppKit 原生组件，从根上降低长会话内存、滚动和窗口缩放压力。
2. 采用微软 SwiftStreamingMarkdown 作为原生流式 Markdown 的基础，但维护一个很小的魏碑固定分支，锁定明确版本和提交，不能浮动升级。
3. 写作编辑器、笔记编辑、Markdown 资料阅读继续使用现有 Milkdown、KaTeX、WebView 链路，本计划完全不迁移它们。因此用户的写作、保存、选区、阅读资料等现有流程不应发生变化。
4. Mermaid 互动图和 GenUI 富回答继续使用各自独立的专用 WebView；普通 Markdown、表格、代码、图片、链接、来源和公式不再使用聊天 WebView。
5. 正式产品只有一条渲染路径：普通会话回答走原生，Mermaid、GenUI 走明确的专用网页块。不要保留旧聊天 WebView 作为回退，不加功能开关，不做两套渲染器并存，不做兼容层。
6. 交付目标不是牺牲能力换性能。标题、段落、列表、引用、链接、表格、代码块、图片、来源、行内公式、块公式、复制、选区、流式生成到定稿都必须正常。
7. 样式在内部技术候选阶段可先用库的配置起步，但最终验收版本必须把字号、颜色、段落间距、表格和代码块视觉调到与现有魏碑会话一致或无明显退步；不为了逐像素复刻另造一套表格或 Markdown 引擎。

## 二、为什么采用微软方案

1. 它不是“微软网页”，而是微软开源的 Swift 原生流式 Markdown 库，面向 SwiftUI、macOS 和 iOS。它解决的正是魏碑会话需要的 Markdown 逐步生成、表格、代码和原生视图组合。
2. 它的价值是少造轮子：原生 Markdown 解析、流式增量呈现、表格和代码等通用能力直接复用，魏碑只维护产品接线和少量确实存在的公式修正。
3. 它本身不是公式引擎。目前公式交给 iosMath，并在公式进入引擎前做了一批会改变含义的替换，这正是不能原样使用的地方。
4. 最终方案不是放弃微软库，而是用微软库做 Markdown 骨架，修掉它的公式预处理问题，并把底层公式渲染换成更合适的 SwiftMath。

## 三、依赖与小型固定分支

1. 以 SwiftStreamingMarkdown v0.7.0（上游提交 `5f7c04e0558df6146f90d482edb62cb456986bda`）为基线，锁定魏碑公开固定分支提交 `e3b6e952a7121e95aecb5370c90459b5c800fdf1`。源码和许可证已重新确认，使用 MIT License，不使用浮动版本号。
2. 魏碑维护一个最小分支，只包含完成本计划必需的改动：
   - 删除有损公式改写；
   - 接入 SwiftMath；
   - 带入已确认需要的行内公式背景修复；
   - 暴露魏碑需要的少量样式和图片配置。
3. 不把微软整个仓库大改成魏碑专用框架，不重写 Markdown 解析器，不建设插件体系，也不预留“以后可能用”的抽象。
4. SwiftMath 同样锁定魏碑公开固定分支提交 `c7830ce1ee79de0c57e4eac1ed3405b1ec790898`（上游基线 `1d2c90827e9c3908269d810d055fb03b7da5fd53`），许可证为 MIT License。它负责真正把 LaTeX 数学语法画成 macOS 原生视图；它使用 AppKit、CoreText、CoreGraphics，适合 macOS 原生应用。
5. 新依赖必须明确写入包管理配置；不复制源码散落进主工程。

## 四、公式必须怎么修

### 4.1 删除微软库的有损公式改写

必须删除所有会把用户或模型原公式改成另一种命令的规则，而不是只修两个例子。包括但不限于：

- 把 `\tfrac`、`\dfrac` 改成 `\frac`；
- 把 `\overrightarrow` 改成 `\vec`；
- 把 `\implies` 改成 `\Rightarrow`；
- 把 `\rightleftharpoons` 改成 `\Leftrightarrow`；
- 删除 `\boxed` 或尺寸相关命令；
- 其他会改变排版或数学含义的替换。

原因：`\tfrac` 是行内紧凑分式，`\dfrac` 是展示型大分式，`\frac` 是普通分式；它们不是同一个视觉和语义。宽帽子、长箭头、反应可逆箭头、方框等也不能被偷偷降级。魏碑应把原公式完整交给真正的公式引擎。

### 4.2 魏碑只保留不改变语义的输入整理

只允许做下面这些结构性整理：

- 统一识别公式定界符；
- 对现有历史里已经确认的明显错误括号或 hat 参数做最小修正；
- 流式生成时，只对无歧义的未闭合 `\(`、`\[`、`$$` 公式尾巴暂不提交，等后续字符补齐；单个 `$` 与货币文本天然歧义，未闭合时保持原文可见，不靠数字、字符类别或命令形态猜测；
- 不改数学命令，不删命令，不把复杂命令降成简单命令。

支持的入口至少包括：

- 行内 `$...$`；
- 行内 `\(...\)`；
- 块级 `$$...$$`；
- 块级 `\[...\]`；
- 魏碑历史中已有的伪括号公式写法，只做明确、有限的归一。

### 4.3 用 SwiftMath 替换 iosMath

1. 在微软库的公式视图提供层接入 SwiftMath，使用它的 macOS 原生数学标签或视图。
2. 必须确认并支持魏碑真实历史中出现的：
   - `\frac`、`\tfrac`、`\dfrac`；
   - `\hat`、`\widehat`；
   - 根号、求和、偏导、上下标、大括号；
   - 行内公式和块公式；
   - `\text{中文}`；
   - 中文全角标点与公式混排；
   - 正文不同字号档位下的公式跟随。
3. 配置系统字体作为公式文本段的后备字体，确保 `\text{中文}` 不缺字、不变空白。
4. 公式解析错误不能静默吞掉或显示空白。开发版本和自动检查必须直接暴露具体错误；正式交付前，真实样本中的任何解析失败都算阻断问题，必须修好，而不是接受“显示源码”作为交付方案。
5. 不建设公式 WebView 回退，不并存多个公式引擎，不做复杂的“先试 A、失败换 B”。

## 五、会话里的原生渲染接线

1. 新建一个职责单一的会话原生 Markdown 视图，例如“智能体原生 Markdown 视图”，实现文件名按工程规范确定。它只负责：
   - 接收完整 Markdown 文本；
   - 接收正在生成或已完成状态；
   - 应用魏碑字号、颜色、主题、链接和图片配置；
   - 输出原生 SwiftUI 内容。
2. 模型流式生成时，把供应商每次真实进度携带的完整累计文本直接传入同一个视图，由 SwiftStreamingMarkdown 处理增量显示。删除旧的逐字符显示泵，不再用计时器、字符批次或积压阈值把一次真实进度拆成更多快照；也不要每个碎片重建一棵网页。
3. 从正在生成到回答完成必须保持同一个可见表面，最后一帧只提交最终文本和完成状态，不能出现先消失再重建、闪白、高度跳变或字体突然变化。
4. 历史已完成回答使用静态原生 Markdown 视图；当前正在生成的回答使用流式视图。两者共享同一主题配置和同一内容组件，不做两套样式。
5. 替换全部真实会话入口：
   - 主聊天里的 assistant 回答；
   - 选区浮动问答；
   - 当前流式回答；
   - GenUI 前后夹着的普通文字片段。
6. 用户消息、系统错误等本来就是简单文本的内容，继续使用现有轻量原生文本，不扩大改动。
7. 保留整条消息复制，复制的是原始 Markdown 内容；保留现有文字选择行为。
8. 来源标签继续使用现有原生界面和现有点击定位逻辑。不要因更换正文渲染器改变来源标签的数据结构。
9. 图片通过微软库的图片配置接到魏碑现有资源解析和安全读取路径；不要另造下载器、图片缓存或远程白名单系统。

## 六、Mermaid、GenUI 与 HTML 的明确处理

### 6.1 Mermaid

1. Mermaid 不是普通 Markdown 原生能力。把完整的 Mermaid 代码围栏识别为独立 Mermaid 内容块。
2. 该块使用专用 `WKWebView`，复用魏碑现有本地 Mermaid 运行时、主题、尺寸回传和交互能力。
3. 流式阶段围栏未完成时先作为普通代码内容稳定显示；回答完成且围栏完整后，生成 Mermaid 块。不要每收到几个字符就销毁或重建网页。
4. 退役会话日志中已查到 6 条唯一 Mermaid 输出，当前可见会话中另有 1 条；两组都必须纳入真实验收，不用重复记录凑数。

### 6.2 GenUI

1. GenUI 是明确的可交互富回答协议，继续使用现有独立网页运行时。
2. 它需要的 JavaScript 和本地桥接继续保留。本计划绝不是全应用禁止 JavaScript。
3. 不重写 GenUI，不把它强行塞进普通 Markdown 原生组件。

### 6.3 普通 HTML

1. 已扫描本机现有 assistant 历史，没有发现普通回答依赖任意原始 HTML 标签；因此本计划不为不存在的需求建设“任意 HTML 网页块”。
2. 普通回答中的原始 HTML 不作为可执行网页运行。它按原生 Markdown 库的可读文本规则呈现；需要交互网页能力的正式入口只有 Mermaid 和 GenUI。
3. 这不是为了做安全阉割，而是为了避免模型随手输出 HTML 就重新制造每条回答一个 WebView、JavaScript 生命周期和内存问题。
4. 如果以后真的出现独立的 HTML 产品需求，另立功能和协议评审，不在本计划里预埋浏览器容器。

## 七、同一次替换中删除旧聊天 WebView 防御体系

新的普通回答原生渲染接通后，在同一条交付线上删除旧链路，不保留过渡代码。

必须删除：

1. 判断回答是否需要网页渲染的旧分类器以及对应源码自检。
2. 聊天 Markdown 网页启动队列、其模型和测试。
3. 完成态 Markdown 高度缓存、LRU、宽度分桶、冻结高度等逻辑和测试。
4. 三屏外判断、离屏占位、占位行、可见性探针及相关测试。
5. 0.01 透明度预热、骨架态、网页交接态等为了隐藏 WebView 启动的状态。
6. `rendererSurfaceMounted`、`finalizedRendererReady`、`awaitsFinalizedRendererReady`、`keepsMarkdownSurfaceMounted`、`usesFinalizedKaTeX` 等只服务旧聊天 WebView 生命周期的字段和分支。
7. 聊天专用的 `MarkdownPreviewView`、紧凑预览网页路径、聊天宽版网页字体规则、Web 流式桥接、Milkdown 聊天流式插件和聊天专用网页动画。
8. 只删除聊天使用的链路；笔记编辑和 Markdown 阅读仍依赖的 `RichMarkdownEditorView` 核心必须保留。
9. 同步删除旧“最初只显示最近 30 条、点击再展开 30 条”的消息上限、策略、按钮和测试。
10. 聊天消息列表改为标准 `LazyVStack` 渲染全部消息。保留跳到最新、用户正在底部时自动跟随、搜索定位、来源定位。
11. 不新建自定义虚拟列表、高度预测、视区缓存、AppKit 列表、后台预热或另一套回收框架。普通原生行交给系统懒加载即可。
12. 仓库旧注释记录过 `LazyVStack` 搭配 WebView 会冻结；本次前提已经改变，因为普通行不再挂 WebView。必须通过真实 100+ 条消息快速滚动验证，而不是保留旧架构。

## 八、样式与用户体验

1. 正式交付要求用户写作和资料阅读体验完全不变，因为那两套界面不在改动范围。
2. 会话功能不能回退：
   - Markdown 结构完整；
   - 表格可读，列宽、表头、分隔线、内边距与现有风格一致或无明显退步；
   - 代码块背景、字体、复制和横向内容可用；
   - 公式准确、清晰、与正文基线和字号协调；
   - 链接可点；
   - 图片正常；
   - 来源标签和定位正常；
   - 文本可选择、整条可复制；
   - Mermaid、GenUI 仍可互动。
3. 实施时先用库现有主题配置完成技术候选，随后只调整现有配置能覆盖的字号、颜色、间距、表格和代码块样式。不要一上来写自定义表格布局或重新实现 Markdown。
4. 如果真实候选出现明确的视觉缺口，先判断库已有配置或组件能否解决；只有确实无法满足用户可见验收时才补最小定制。
5. 不接受“为了性能先把公式显示源码、表格变纯文本、互动图失效”这类虚假交付。

## 九、实施顺序

- 从最新 `origin/main` 创建独立 worktree 和单独分支。

- 一条功能分支、一个最终 PR；中途不把半套双渲染状态合进 `main`。

### 第 1 步：固定依赖与修公式基础

- 固定微软库基线和提交；
- 建魏碑最小分支；

- 换成 SwiftMath；
- 配中文字体后备；
- 完成唯一的公式合同检查；
- 确认 macOS 14 工程可编译。

完成条件：真实公式语法进入引擎前不被改写，样本全部成功生成非空原生公式视图。

- 接入主题、链接、图片和复制；
- 先替换主聊天中的一条真实生产路径，在隔离候选 App 内检查实际效果。

完成条件：普通文字、列表、表格、代码和公式在真实流式回答中工作，普通回答不创建 `WKWebView`。

### 第 3 步：覆盖全部会话入口

- 选区浮动问答；

### 第 4 步：独立 Mermaid 接线

- 从普通 Markdown 内容中拆出完成的 Mermaid 围栏；
- 用专用网页块复用现有本地 Mermaid 能力；
- 验证退役日志中的 6 条唯一 Mermaid 输出和当前可见会话中的 1 条；
- GenUI 保持原样。

完成条件：普通回答原生、Mermaid 和 GenUI 网页化的职责边界清楚，不发生网页嵌套或全消息 WebView。

### 第 5 步：删除旧防御体系与 30 条限制

- 按第七节清单删除旧分类器、启动队列、高度缓存、占位回收、预热状态、聊天网页桥接和相应测试；
- 更新仍在断言旧源码文本存在的自检；
- 删除 30 条分页展示；
- 改成标准 `LazyVStack` 全历史消息。

完成条件：旧聊天 WebView 生命周期代码和死测试不再存在，构建和保留的检查通过。

### 第 6 步：样式收口与真实验收

- 对照当前魏碑会话调整字号、颜色、间距、表格和代码块；
- 运行真实中文长回答与历史长会话；
- 只修实际观察到的缺口，不扩建新框架。

建议工期 6–8 个工作日：

- D1：固定分支并清理公式预处理；

- D3：原生包装和流式；
- D4：全入口替换；

- D8：真实验收与修复实际问题。

## 十、只保留必要检查

### 10.1 一个新增自动检查

在魏碑维护的 Markdown、公式分支里只增加一个“公式合同检查”方法，集中放入这些真实语法：

- `frac`、`tfrac`、`dfrac`；
- `hat`、`widehat`；
- `beta`；
- 中文 `text`；
- 根号、求和、偏导、大括号；
- 行内和块级定界符；
- 未完成的流式公式尾巴。

只验证两件事：

1. 预处理没有改变原公式命令；
2. 完整样本都能解析并产生非空结果，未完整尾巴会等待而不是闪错。

不要把每个公式拆成一套测试，不建随机公式、主题截图矩阵、宽度矩阵或模型评分。

### 10.2 更新现有交付检查

- 删除或改写仍然要求旧聊天 WebView、高度缓存、占位窗口存在的源码文本断言；
- 保留真正验证编辑器、阅读器、数据安全和构建的现有检查；
- 不为了让门禁变绿保留死代码。

### 10.3 一次真实 App 验收

必须使用独立候选 App 完成一条完整验收：

1. 打开或制造 100+ 条消息的真实会话；
2. 连续快速滚动约 60 秒；
3. 反复缩放窗口，尤其测试启动后的第一次快速缩窄；
4. 让真实模型生成含中文标题、列表、表格、代码、行内公式和块公式的长回答；
5. 从开始生成一直看到定稿，确认不闪白、不重置、不跳高；
6. 检查退役 AgentRuntime/Pi 日志中的 17 条含公式回答和当前可见会话中的 4 条，重点包括 `\widehat{wage}`、`\tfrac`、`\dfrac` 和中文数学文本；
7. 检查选区、复制、链接、来源标签及定位；
