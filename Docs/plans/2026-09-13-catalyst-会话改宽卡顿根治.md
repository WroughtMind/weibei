# Catalyst 会话改宽卡顿根治

2026 年 9 月 13 日。用户反馈：最新版（Catalyst 会话路线，main@f81a1e7f）会话内容一多或一复杂，拖动分栏 / 改窗口宽度就明显卡顿；内容少则正常。要求在不回退任何已验收能力（实时重排、阅读位置保留、富内容、选择复制）的前提下根治。

## 根因（读码实证，行号以 main@f81a1e7f 为准）

`App/Sources/ConversationController.swift:155-197` `viewDidLayoutSubviews`：每一帧宽度变化都同步执行

```
for message in messages { for block in message.blocks { store.measure(block, width: bodyWidth) } }
flow.invalidateLayout(); collection.layoutIfNeeded()
```

- 可见与屏幕外的**全部**段落每帧都重新走一遍 CoreText framesetter 测高（`PreparedContent.swift:196-206`）。
- 非纯文本段（代码 / 表格 / 引用 / 图片）没有可脱离视图的布局对象，测高要走 `view(for:)`：不在视图池里的会**新建 BlockView 并完整渲染**，池上限 36，超出即淘汰，下一帧再建（`PreparedContent.swift:150-193`）。
- 每条可见消息的 SwiftUI 页脚（用户气泡等）改宽后各自异步回报高度，`updateAuxiliaryHeight` 每次都单独做一轮 `invalidateLayout + layoutIfNeeded + 锚点恢复`（`ConversationController.swift:427-437`），一帧里重复多次。

历史证据（`App/Evidence/*.json` 的 `resize_ms`）：517 段 43～278 ms / 次，19 段含图 3212 ms / 次。用户机器上 120 条消息、14 个代码块的真实会话正落在这个量级。

## 方案

保持「拖动中文字实时跟随宽度」这一已验收行为，只改**每帧做多少**：

1. **拖动帧只重排屏幕上的段落**：宽度变化时只对当前可见 item 的段落测高，屏幕外段落沿用上一次高度作为估计，`sizeForItemAt` 直接返回；滚入视口时按需测高（`store.view(for:)` 原本就会在 `block.width != width` 时补测）。
2. **停手后分片收敛**：宽度停止变化约 50 ms 后，由 CADisplayLink 驱动，每帧用约 4 ms 预算按「离视口最近优先」测量剩余段落，每片结束做一次布局刷新并恢复阅读锚点，直到全部段落在新宽度下高度收敛。再次拖动即取消并重排。
3. **首次布局仍同步全量测高**：打开历史会话的路径不变，避免首屏行为回退。
4. **页脚高度回报合并**：多条页脚同帧回报只做一次布局刷新。
5. **懒测高的自纠正**：cell 配置时若段落高度与布局属性不一致，合并安排一次布局刷新。

## 验证

- 新增验收自检「拖动只重排可见段落，停手后收敛且阅读段落不变」：history 场景 240 条，连续 12 步收窄，逐步断言测量数 ≤ 该步前后可见段落数之并集、`bodyWidth` 已实时应用、可见段落视图宽度已跟随；停手后等待收敛，断言全部段落宽度一致且阅读锚点消息 / 段落不变。会话自检由 11 项变 12 项（`App/script/check-ci.sh` 同步）。
- `resize_ms` 改前 / 改后同机对照（隔离身份验收包，`--self-check`），记录 p50 / p95 / max；这些是组件耗时，不称为帧率。
- 完整 CI（含 Catalyst 双架构检查）。

## 实施记录（2026-09-13）

改动只在 `App/Sources/ConversationController.swift`（会话控制器）以及自检计数（`App/script/check-ci.sh`、`App/README.md`）：

- 改宽帧：`reflowVisibleParagraphs()` 只测量当前布局中可见区域（含下方 20% 余量）内、宽度尚未跟上的段落；首次布局仍全量测高。
- 停手收敛：`scheduleWidthConvergence()` 在宽度停止变化 50 ms 后启动 CADisplayLink，每帧 4 ms 预算按离视口最近的顺序测量剩余段落；全部完成后做一次带阅读锚点的布局刷新。再次改宽即取消重来。
- 页脚高度与懒测高的自纠正统一走 `requestLayoutRefresh()`，同一轮主线程只刷新一次布局。

## 第二轮（2026-09-13）：快速来回拖动仍有卡顿

用户在第一轮候选上反馈：好了非常多，但快速来回拖动仍有卡顿。用真实三栏分栏做 20 秒正弦来回拖动（`--drag-profile`，隔离身份验收包，240 条历史），按显示回调间隔计数：

| 场景（对话 240 条） | 改前 main@f81a1e7f | 第一轮 | 第二轮 |
|---|---|---|---|
| 对话 \| 笔记 分隔线，±140 pt | 中位 50 ms，>33 ms 317 次，累计停顿 20.0 s | 中位 16.7，>33 ms 152 次，11.6 s | 中位 16.7，>33 ms 7 次，0.45 s |
| 阅读 \| 对话 分隔线，±140 pt | 中位 66.7，226 次，19.9 s | 99～166 次，13.7 s | 4 次，0.20 s |
| 阅读 \| 对话，±320 pt | 未测 | 未测 | 9 次，0.47 s |
| 对话 \| 笔记，真实资料 + 笔记已打开 | 未测 | 154 次，9.1 s | 6 次，0.45 s |

采样（`sample` + dSYM 符号化）定位到第一轮之后剩余的三处每帧开销，均在会话控制器之外：

1. **流式布局对象每帧全量重建**：`UICollectionViewFlowLayout.prepare` 对每个 item 重新查尺寸并建行，240 条 × 若干段 ≈ 1200 个 item，每帧 3～50 ms。改为自定义 `ConversationLayout`（`App/Sources/ConversationLayout.swift`）：一列纵向堆叠，宽度变化只做一次线性累加，可见区域用二分定位。
2. **轨道条与面板标题每帧重算 SwiftUI body**：对话窗格的 GeometryReader 每帧把新宽度传给 `ContentRailView` 与 `WeiBeiPaneHeader`，前者 240 条轨道刻度按钮的 ForEach 整棵重算，轨道条目本身又是每帧对全部消息跑正则。改为：轨道视图与标题视图实现 `Equatable` 并 `.equatable()`，宽度先量化到档位（标题 3 档、轨道 16 pt 步进）；轨道条目按「消息 ID 列表 + 末条文本长度 + 语言」缓存（`AgentRailMemo`）。阅读窗格与笔记窗格的轨道一并受益。
3. **排版档位在阈值附近来回翻转**：`comfy` 由每帧实时宽度决定，跨过 620 pt 时全部消息换字号（一次 34 回主题切换，每回整表重建）。Catalyst 下拖动中改用 `heldPaneLayoutWidth` 决定档位，停手后随最终宽度一次落定。

其余小项：拖动期间页脚高度回报延后到停手后统一刷新；隐藏的 fixture 输入控件不再每帧改 frame；可见纯文本段经 label 自身测高让 Litext 复用测量结果；拖动锚点在整个手势内复用，阅读行不漂移。

验收工具：`CatalystBusinessCheck.runDragProfile`（仅验收构建，隔离 `.dragprofile` 身份），驱动真实分隔线做 20 秒来回，记录显示回调间隔、逐窗格布局耗时、长轮次 CPU/墙钟。12 项会话自检全部通过（含快速来回 60 帧采样）。

### 第二轮修正（用户反馈两条）

1. **轨道条不再响应**：第二轮给轨道视图和面板标题加的 `.equatable()` 在真实使用中让轨道停止响应（等值比较跳过了它需要的更新），已撤回；宽度量化也一并撤回。轨道条目的缓存（`AgentRailMemo`）保留。撤回后同机拖动对照仍是满帧（>33 ms 11 次，累计 0.8 s），说明大头在列表布局与排版档位两项。
2. **开第三栏时比例回到均分**：这是主线原有行为（`paneWidths` 对「新开一栏」一律均分），不是本轮引入。改为：新开的一栏拿均分份额，已在屏幕上的栏在剩余空间里保持原比例。验收构建新增 `--pane-open-check`：两栏拖到 0.587 的比例后打开第三栏，比例仍为 0.587。
