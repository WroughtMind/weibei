# 0.0.1 首版候选与发布收尾

用户目标：最新候选包、完整验收、发布说明全部完成，发现问题直接修，交付可以发版的结果。起点为 `main@65a1a717`。版本沿用 0.0.1，安装路线沿用两种芯片分别打包、未经 Apple 公证、更新包签名校验。

## 本轮范围

- 更新首版发布正文、应用内摘要、中英文安装介绍与官网上手说明。
- 修复发布资产目录不一致；候选验证也完成双架构汇总、更新清单、安装描述、调试符号和发布说明装配。
- 通过现有完整检查、两种芯片真实应用检查及最终安装包验证。真实窗口操作在隔离桌面进行。
- 对最终候选记录版本、构建号、源码、安装盘和清单校验值，形成可复核的交付目录。
- 本轮终点为可发布候选；公开标签和版本另按明确发布指令执行。

## 已确认的发布问题

原发布流程的上传输入同时包含 `dist/release/<arch>/…` 与 `dist/package-<arch>.json`，上传根目录因此为 `dist`；下载后文件在 `release/<arch>/…`，汇总却在根目录寻找安装盘。正式公开阶段才执行汇总，普通候选验证不会发现问题。目录行为参见 [GitHub 上传工具说明](https://github.com/actions/upload-artifact#upload-using-multiple-paths-and-exclusions)。

修复方式：将同一架构的发布输入放在同一目录，汇总成为独立步骤并在候选验证时执行；公开阶段只消费已汇总并校验的文件。发布正文使用随版本维护的完整说明。

## 验证安排

| 阶段 | 验证内容 | 完成依据 |
|---|---|---|
| 本地相关检查 | 工作流路由、脚本语法、官网组装与中英文链接、发布工具检查 | 保留命令和结果 |
| 合并检查 | 最新主线组合的必需检查，包含两种芯片应用与安装包路径 | 检查对应精确提交 |
| 最终候选 | 干净主线的完整专项检查与发布流程，关闭公开选项 | 主线提交、两个工作流及完整候选集合对应 |
| 交付复核 | 独立验签、安装盘挂载、版本与架构、更新引擎、核心场景与错误场景 | 记录实际产物与验收证据，未覆盖项不记通过 |

真实体验表使用“用户怎么操作 / 应该看到什么 / 是否通过 / 问题备注”四列，随最终候选交付。后续若发现问题，只复验受影响路径及本次必要发布验证。
