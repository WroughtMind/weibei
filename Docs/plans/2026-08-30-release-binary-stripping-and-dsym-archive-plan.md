# 魏碑发布二进制符号裁剪与调试符号归档计划

日期：2026-08-30  
状态：方案已锁定，待实施  
范围：候选包与正式发布包的主可执行文件

## 一、结论与定位

这是一次性的打包流水线优化，不是每个 PR 手工做一次。实现合入后，每次生成候选包或正式发布包时自动执行“生成调试符号文件 → 裁剪正式二进制 → 签名”；普通开发构建和普通 PR 测试保持未裁剪，方便调试。

当前同一次最新主分支发布构建的实测基线：主可执行文件从 27,328,552 字节（27.33MB）裁剪到 11,267,056 字节（11.27MB），减少 16,061,496 字节，约 58.8%。这个数字只针对主可执行文件，不代表整个 App 或 DMG 同比例缩小。

主要收益是降低候选包、正式包的下载与磁盘占用。它不是运行内存优化；冷启动可能因磁盘映射内容减少而略有改善，但必须实测，计划不承诺启动收益。

## 二、范围

第一版只处理魏碑主可执行文件：

- 只接入候选包和正式包共用的正式打包入口；
- 只裁剪 release 主可执行文件；
- 每次构建都生成与该二进制严格对应的 dSYM 调试符号文件；
- dSYM 保存在用户安装包之外，作为内部构建证据归档；
- 开发版、调试版、普通 `swift build`、普通 PR 检查不裁剪；
- 不顺带处理资源压缩、图片压缩、Sparkle 框架、辅助程序或其他性能问题。

## 三、固定打包顺序

正式打包入口必须按以下顺序执行，不能调换：

1. 从明确的提交构建 release 主可执行文件；
2. 把未裁剪二进制复制到候选 App 组装目录；
3. 对这份未裁剪二进制运行系统自带 `dsymutil`，生成本次构建专属 dSYM；
4. 验证 dSYM 已生成且与二进制 UUID 一致；
5. 对 App 内的主可执行文件运行已实测的保守裁剪方式 `/usr/bin/strip -x`；
6. 继续现有资源、框架和 App 组装；
7. 按现有规则签名嵌套内容和整个 App；
8. 验证签名后再生成 DMG、执行公证或其他后续发布步骤。

必须先生成 dSYM、再裁剪、最后签名。裁剪签名后的文件会破坏签名，因此禁止把裁剪放在签名之后。

第一版固定使用已经验证过的 `strip -x`，只移除非运行必需的局部符号，不改用更激进的全符号删除方式。

## 四、dSYM 归档规则

- 每次构建生成独立 dSYM，不能复用旧版本；
- dSYM 文件名或所在目录必须能定位版本号、内部构建号和提交 SHA；
- dSYM 不放进 `.app`、DMG 或用户下载包；
- dSYM 不提交进 Git；
- 候选包阶段保存在本次构建产物目录旁；正式发布时沿用现有内部构建产物保存位置；
- 若 dSYM 生成、完整性检查或 UUID 匹配失败，打包必须失败，不允许静默继续并产出无法符号化的正式包。

## 五、最小实现原则

- 复用现有候选包、正式包的唯一打包脚本，不建立第二套打包流程；
- 使用 macOS 自带 `dsymutil`、`strip`、`dwarfdump`、`codesign`，不增加依赖；
- 只在一个共享打包入口加入步骤，不要求每个 PR 作者记住手工命令；
- 不添加用户设置、环境开关或运行时代码；
- 不把当前 11.27MB 写成永久生产常量，因为源码增长会改变绝对体积。

## 六、验证

用同一提交、同一 release 构建完成以下检查：

1. 记录裁剪前后主可执行文件字节数；裁剪后必须确实小于裁剪前；
2. 本次任务验收应复现约 58.8% 的降幅；若明显低于 50%，先调查原因，不把 50% 做成长期硬编码门槛；
3. 使用 `dwarfdump --uuid` 确认 App 二进制与 dSYM UUID 完全一致；
4. 确认 dSYM 中存在可用于符号化的调试信息；
5. 使用 `file` 或 `lipo` 确认架构未改变；
6. 使用 `otool -L` 确认动态依赖未改变；
7. 使用 `codesign --verify --deep --strict` 验证最终 App 签名；
8. 从临时候选 App 启动一次，完成打开工作区、打开材料、进入智能体界面的轻量冒烟；
9. 若进入正式发布链路，现有公证、装订和更新包检查必须继续通过。

打包脚本需要保留一个最小自动检查：dSYM 存在、UUID 匹配、裁剪后体积小于裁剪前、最终签名通过。不要为此新建测试框架或体积基准系统。

## 七、实施顺序

### 阶段一：一次性流水线改造

- 找到候选包与正式包共用的真实打包入口；
- 在该入口加入 dSYM 生成、UUID 校验和 `strip -x`；
- 确保裁剪发生在签名前；
- 给每次构建的 dSYM 加入可追溯命名。

### 阶段二：同提交前后验证

- 用同一 release 构建记录 27.33MB → 11.27MB 级别的对照；
- 完成 UUID、架构、依赖、签名检查；
- 确认 dSYM 不进入用户包。

### 阶段三：候选包验收

- 从改造后的唯一入口生成临时候选 App；
- 完成轻量真实 App 冒烟；
- 在后续获正式发布授权时，确认公证、DMG、更新链路不受影响。

## 八、完成标准

只有同时满足以下条件才算完成：

- 以后每个候选包和正式包自动裁剪，无手工步骤；
- 普通开发与 PR 测试构建不受影响；
- 每个包都有匹配且可追溯的 dSYM；
- 主二进制体积显著下降，当前基线复现约 58.8%；
- 架构、动态依赖、签名和真实 App 启动正常；
- dSYM 未进入用户安装包，也未提交 Git；
- 汇报明确区分“主二进制缩小”与“整个 App/DMG 缩小”，不宣称已降低运行内存或已提升启动速度。

## 九、明确不做

- 不要求每个 PR 单独手工裁剪；
- 不裁剪 debug 或普通开发构建；
- 不把 dSYM 发给用户；
- 不顺带压缩资源、框架和辅助程序；
- 不建立长期固定体积门槛或体积监控平台；
- 不把这项工作描述为内存优化；
- 不在本计划中处理启动性能、长会话内存或其他运行效率问题；
- 不在未获发布授权时创建正式 Release、上传安装包或改变发布状态。
