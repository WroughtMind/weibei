# Native Agent 滚动上下文压缩计划

日期：2026-08-30  
状态：方案已锁定，待实施  
范围：Assistant 与未来 Tutor 共用的模型上下文滚动压缩

> 本计划从 Pi 真正借鉴的只有五个核心动作：**按容量触发、选择安全切点、生成滚动摘要、让模型看到“摘要＋近期原文”、下一次用“旧摘要＋新退出内容”更新摘要**。
>
> **四套服务商用量解析、多阶段降档压缩、本地账本性能索引、复杂重试，不是这份第一版计划的组成部分。**

## 1. 产品机制

魏碑采用 Pi 式滚动上下文压缩，但压缩对象只是“下一次发给模型的上下文”，不是用户数据：

1. 根据模型上下文容量判断是否需要压缩；
2. 在完整对话结构中选择安全切点；
3. 第一次把较早历史总结成一个滚动摘要；
4. 模型后续只看到“最新摘要＋近期原文”；
5. 再次触发时，用“旧摘要＋这次新退出窗口的历史”更新为一个新摘要。

以下产品约束必须保持：

- 用户可见聊天不删除、不折叠、不替换；
- 完整运行账本不删除，原始事件始终保留；
- 旧消息只是退出模型上下文，不退出用户界面和本地记录；
- Assistant 与未来 Tutor 共用同一套压缩机制，不分别实现；
- 压缩对用户透明，不增加手动压缩按钮、压缩设置、后台压缩任务或摘要展示。

## 2. 先统一真实模型上下文

压缩成立的前提，是容量判断、摘要生成和正常发送看到同一份真实请求。

### 2.1 本轮定位必须进入账本

当前阅读材料、页码等本轮最小定位信息，应在用户模型消息写入账本时一并持久化。不得继续在真正发送给模型前临时追加，因为临时内容会造成以下三条链路不一致：

- 正常发送实际包含定位；
- 容量估算没有计算定位；
- 摘要输入无法稳定复现定位。

完成后，账本事件本身应足以重建模型当时真正看到的用户消息。

### 2.2 三条链路复用同一最终请求

正常发送、容量估算、摘要历史输入必须复用同一个模型可见投影和最终请求，不得各自拼装消息。最终请求包括：

- 系统提示；
- 模型消息；
- 工具定义；
- 工具参数与结果；
- 图片内容；
- 本轮已持久化的材料、页码等定位。

每次主循环只派生一次消息。容量估算直接检查这次派生形成的最终请求；需要摘要时，从同一份投影中截取退出窗口，不再重新派生账本消息。

## 3. 第一版容量判断

### 3.1 已知模型上限

在现有模型路由中增加一份最小映射，只维护魏碑内置且明确支持的模型上下文上限。它是路由信息的一部分，不扩建成模型能力数据库。

- 内置且已确认的模型：按映射执行主动压缩；
- 用户手输的未知模型：不猜测上限，第一版不承诺主动压缩；
- 未知模型继续走正常调用和现有错误流程；
- 不为此增加设置表单、模型信息表或用户配置。

### 3.2 本地保守估算

第一版使用一个统一的本地保守估算器检查最终请求，不把四套服务商的 token 用量解析作为前置条件。估算必须覆盖：

- 中文与英文文本；
- 系统提示；
- 工具定义；
- 工具调用参数与工具结果；
- 图片输入。

估算以宁可略高、不可漏算为原则；所有调用方复用同一入口，不为不同服务商复制四套计算路径。

### 3.3 固定触发规则

内部触发规则固定为：

```text
回答预留量 = min(16_384, 上下文上限 / 4)
输入警戒线 = 上下文上限 - 回答预留量

当且仅当：估算后的最终输入 > 输入警戒线
才触发压缩。
```

这两个数值是内部机制，不提供用户可调参数。

## 4. 账本检查点

### 4.1 删除未使用的旧结构

删除当前未使用的 `surface/replace` 事件，以及消息下标替换字段。第一版不保留兼容层，也不让两套替换机制并存。

### 4.2 新增唯一检查点

新增 `contextCompaction` 检查点。除事件公共封装外，它的有效载荷只保存：

- `summary`：最新滚动摘要；
- `firstKeptSeq`：仍作为近期原文进入模型上下文的第一条原始事件序号。

不额外保存压缩原因、服务商、模型、用量报表、旧摘要数组或其他运行状态。

### 4.3 最新检查点投影规则

账本投影时只使用最新的 `contextCompaction` 检查点：

1. 向模型上下文注入一条内部 `user` 摘要消息；
2. 再派生 `firstKeptSeq` 及之后的原始事件；
3. 更早的检查点和更早的原始事件不再进入模型上下文；
4. 所有原始事件仍完整保留在账本中。

摘要是模型内部上下文，不进入用户可见聊天。

## 5. 安全切点

程序只判断容量和对话结构边界，不负责从历史中提取“目标”“误区”或判断语义重要性。

切点规则按以下顺序执行：

1. 优先在完整 `turn` 结束处切分；
2. 当前单轮因为工具循环过长时，允许在已经完成的 `stepEnd` 后切分；
3. 工具调用与对应工具结果必须作为一个整体，永不拆开；
4. 未完成的步骤永不进入摘要窗口；
5. 近期原文最多保留约 20k token；上下文容量较小时，按实际可用空间缩小近期窗口；
6. `firstKeptSeq` 必须落在满足以上条件的原始事件边界。

如果单条消息本身已经超过模型容量，第一版不建设分块系统，沿用正常错误流程。

## 6. 摘要生成

### 6.1 调用方式

摘要直接复用当前会话所选模型与现有适配器：

- 不提供工具；
- 不联网；
- 使用低推理档；
- 最大输出 8k token；
- 输出普通文本或 Markdown，不使用 JSON。

### 6.2 第一次与后续更新

- 第一次压缩：输入较早历史，生成第一个滚动摘要；
- 后续压缩：输入“上次摘要＋这次新退出窗口的历史”，更新成一个新摘要；
- 始终只保留一个最新摘要，不累积多个摘要。

摘要所使用的历史片段必须来自本次主循环已经派生的同一份模型可见投影，不再独立重建消息。

### 6.3 摘要提示词契约

提示词使用通用的“延续对话摘要”，不照搬 Pi 面向编程任务的固定 `Goal / Progress / Next Steps` 模板。

仅在相关内容真实存在时保留：

- 当前正在讨论的问题；
- 用户表现出的理解与困惑；
- 用户给出的纠正，且最新纠正优先；
- 已经解释或尝试过的内容及其效果；
- 尚未结束的问题；
- 资料位置、资料名称、数字和来源。

没有的内容不写，不虚构目标、进度、结论或下一步。

## 7. 接入主循环

压缩检查发生在每次真正调用模型之前，并且必须早于写入 `stepStart`。

完整顺序如下：

1. 从账本派生一次模型消息，并构建本轮唯一的最终请求；
2. 查询当前模型的已知上下文上限；未知模型直接继续正常调用；
3. 保守估算最终请求；未超过警戒线时继续正常调用；
4. 超过警戒线时，从同一份投影中选择安全退出窗口和 `firstKeptSeq`；
5. 用当前模型生成或更新候选摘要；
6. 用候选摘要和近期原文重建候选最终请求；
7. 再次估算，确认候选请求已经低于警戒线；
8. 只有摘要成功且候选请求通过容量检查后，才向账本追加 `contextCompaction` 检查点；
9. 写入正常的 `stepStart`，调用模型并继续现有循环。

如果摘要失败，或者重建后仍然超过警戒线：

- 不写检查点；
- 不改变现有账本投影；
- 交给现有错误流程处理。

第一版不增加摘要自动重试、上下文溢出专门恢复、指数退避、多批次摘要、后台队列或压缩状态机。

## 8. 共用边界

滚动压缩属于 Native Agent 运行时的通用上下文能力：

- 当前 Assistant 直接使用；
- 未来 Tutor 接入同一主循环和同一账本投影后自然获得；
- 不为 Tutor 建独立摘要格式、容量规则、检查点或压缩服务。

## 9. 实施顺序

### 阶段一：上下文一致

1. 在用户模型消息写入账本时持久化本轮材料、页码等定位；
2. 删除真正发送前临时追加定位的路径；
3. 每次循环只派生一次消息；
4. 在现有模型路由加入已知模型上下文上限；
5. 加入覆盖最终请求全部组成的本地保守估算。

阶段一完成后，正常发送、容量估算和未来摘要输入必须已经建立在同一模型可见投影上。

### 阶段二：压缩闭环

1. 删除 `surface/replace` 和消息下标替换字段；
2. 实现最新 `contextCompaction` 检查点投影；
3. 实现安全切点；
4. 实现首次摘要和滚动摘要更新；
5. 在模型调用前接入容量检查、候选重建和成功后落检查点的闭环。

### 阶段三：真实应用验收

使用正常模型进行一段真实中文长会话，验证模型在发生滚动压缩后能否继续掌握：

- 用户最近的纠正；
- 正在阅读的材料位置；
- 已经讲过或尝试过的内容；
- 尚未回答的问题。

没有真实问题暴露时，不继续扩建额外压缩能力。

## 10. 自动检查

本计划只新增以下两项自动检查。

### 10.1 账本投影检查

覆盖一次检查点和二次检查点，确认：

- 原始事件始终保留；
- 模型只看到最新摘要和 `firstKeptSeq` 之后的尾部；
- 更早检查点不进入模型上下文；
- 工具调用与工具结果没有被切开。

### 10.2 完整循环检查

测试适配器使用测试专用的小上下文上限，确认超过警戒线后能够完成“切分、摘要、重建、落检查点、继续回答”的完整循环。

为了在有限夹具中覆盖滚动更新，可以只在上述两项测试的说明和测试注入中人为压低上限、触发多次压缩。该手段不得进入产品机制、正式配置、生产常量或实施阶段。

不新增模型打分、语义基准矩阵、Tutor 专项用例或四服务商用量解析测试。

## 11. 完成标准

只有同时满足以下条件，第一版才算完成：

1. 正常发送、容量估算和摘要输入来自同一模型可见投影；
2. 每次主循环只派生一次消息；
3. 检查点仅保存最新摘要和 `firstKeptSeq`，完整账本和用户聊天不丢失；
4. 安全切点不拆工具调用与结果，不压缩未完成步骤；
5. 两项自动检查通过；
6. 正常模型下的真实中文长会话通过阶段三验收；
7. 产品中没有新增压缩按钮、设置、摘要展示或隐藏的生产调试开关。

## 12. 明确不做

本计划不做以下内容：

- 独立 Tutor 压缩；
- 多摘要；
- 向量记忆；
- 用户目标表单；
- 服务商原生压缩；
- 模型能力数据库；
- 四协议用量统一；
- 后台压缩或手动压缩；
- 本地账本索引；
- 复杂重试；
- 极端模型降档、多阶段压缩；
- 单条超大消息分块。

本计划只解决模型上下文滚动压缩，不顺带处理本地内存、运行效率或启动速度优化。
