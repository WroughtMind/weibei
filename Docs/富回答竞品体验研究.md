# 富回答竞品体验研究

- 调研日期：2026-07-17
- 范围：ChatGPT、Codex、Claude、Gemini、NotebookLM、Microsoft Copilot、Perplexity、Grok、Mistral Le Chat、Manus、Genspark、Replit Agent、Vercel v0、Lovable、Bolt、Gamma，以及 Pi 扩展生态。
- 口径：先记录用户真实看到的回答形态、位置、互动、生成过程和失败体验，再把技术作为解释；优先使用官方页面、官方帮助文档、官方开发文档与本地真实代码证据。
- 证据说明：产品体验分为“官方已明确”“根据多处官方信息归纳”“证据不足，暂不下结论”；旧版魏碑部分另以当前代码树、历史提交和本机旧验收截图复核。

## 总判断

富回答不是一种组件，也不是“比 Markdown 漂亮一点”。成熟产品会根据任务重量，在六种表面之间选择：

| 体验表面 | 用户实际看到什么 | 代表产品 | 适合的任务 |
| --- | --- | --- | --- |
| 消息内增强 | 正文之间出现图表、表格、图片、地图、卡片、小测验 | ChatGPT、Claude、Perplexity | 一眼看懂、一次点击即可完成的轻任务 |
| 并排画布 | 左边继续对话，右边是可编辑文档、代码、网页或学习工具 | ChatGPT Canvas、Claude Artifacts、Gemini Canvas | 需要反复修改、局部选择、版本切换的中任务 |
| 全屏工作面 | 复杂工具接管主要空间，但保留输入框和返回路径 | ChatGPT Apps、Codex、Grok Build | 调参实验、完整应用、长时间执行等重任务 |
| 持久产物 | 回答变成 Pages、站点、幻灯、文件、应用或可分享链接 | Copilot Pages、Sites、Gamma、Manus | 需要保存、协作、导出、发布的成果 |
| 源驱动学习产物 | 围绕资料生成音频、视频、脑图、闪卡、测验、信息图 | NotebookLM、Gemini 学习工具 | 复习、梳理、跨材料理解 |
| 任务工作台 | 用户看到计划、步骤、运行状态、预览、错误、版本和最终交付 | Codex、Replit、v0、Bolt、Genspark | 长时间、多步骤、可验证的生产任务 |

最重要的体验结论只有一句：**富回答自然不自然，取决于它是否像当前疑惑“临时长出的合适工具”，而不是系统为了展示能力塞进来的组件。**

成熟产品还有四个共同点：

1. **自动判断与用户显式要求并存。** 模型可以主动选择，但用户说“只用文字”“画给我看”“做成可调参数实验”时，应当直接覆盖默认判断。
2. **正文与富对象分工，不重复抄写。** 正文负责结论、解释和边界；富对象负责观察、操作、比较和验证。
3. **越重的产物，越要离开消息流。** 小图表可以内嵌，长实验和完整网页应进入侧边或全屏；持久成果再升级为文件、页面或站点。
4. **生成中、失败、修改都是产品的一部分。** 只展示最终截图不算完成；用户必须知道正在做什么、哪里失败、能否降级、如何局部修改。

## 1. Manus

### 用户实际体验记录

| 维度 | 记录 |
| --- | --- |
| 触发场景 | 首页直接给“Create slides / Build website / Design / Create games”等入口；帮助文档区分轻量 Chat mode 和复杂 Agent mode。Agent mode 用于网站、幻灯、视频等复杂任务，消耗 credits；Wide Research 由 AI 自动判断复杂任务是否可拆并触发，不支持用户手动强制触发。 |
| 出现位置 | 官网和帮助文档呈现的是“对话发起任务 → Manus 执行 → 交付结果/任务历史/分享链接”。Wide Research 官方页展示 Manus computer interface 的大截图，强调多个子任务并行运行。Web app 页面强调用对话生成全栈应用并部署。 |
| 具体形态 | 幻灯、网站/全栈应用、视频、研究报告、数据集、图片、后台/数据库/登录/Stripe、SEO 与 analytics。 |
| 可互动能力 | 对网站：部署、analytics、lead 管理、custom domain、full code export、version control/rollback、share permissions、design edit mode。对幻灯：下载 PPTX/PDF/Google Slides，保存到 Google Drive/OneDrive。对任务：分享任务 replay 链接。 |
| 生成中体验 | Agent mode 的重点不是“消息里插一张图”，而是让用户看到任务被拆解、执行和汇总。Wide Research 明确是多 Agent 并行；官网截图强调“多个 subtasks running in parallel”。 |
| 完成后体验 | 完成后交付可部署网站、可下载 deck、完整报告/数据集，支持分享和回滚。Cloud Computer 让高级任务在持久云电脑中继续跑；Desktop “My Computer”让 agent 访问用户授权的本地文件夹和工具。 |
| 错误/不支持体验 | 帮助中心单列 sandbox、high load、browser access、VS Code、website blocked、Cloud Computer uptime 等问题。没有把失败伪装成完成，而是有明确故障入口。 |
| 自然/聪明细节 | Chat mode 不消耗 credits，Agent mode 才做复杂产物；Wide Research 自动触发，避免用户理解技术开关；“设计编辑、回滚、权限、导出”让生成物像真实项目。 |
| 生硬/打断风险 | 产物偏重“完整任务/工程交付”。对魏碑这种学习场景，如果每个回答都升格成任务，会过重；适合材料分析、章节地图、时间线、复杂比较，不适合一句释义。 |

### 技术只作为解释

Manus 的富回答像“任务操作系统”：背后有 Chat/Agent 模式、临时 sandbox、持久 Cloud Computer、本地 Desktop “My Computer”、Wide Research 多子任务。这解释了为什么它能交付网页、幻灯、数据集，而不是只在消息里展示组件。

### 一手证据

- [Manus 首页](https://manus.im/)：入口列出 Create slides、Build website、Design、Create games。
- [Chat mode 与 Agent mode 帮助页](https://help.manus.im/en/articles/11711128-what-are-the-differences-between-chat-mode-and-agent-mode)：说明 Chat 用于即时回答，Agent 用于网站、幻灯、视频等复杂任务。
- [Wide Research 帮助页](https://help.manus.im/en/articles/11960169-what-is-wide-research)：说明自动触发、20 个 subtasks、paid users、credit cap。
- [Wide Research 官方页](https://manus.im/features/wide-research)：展示并行子任务、完整 reports/datasets、官方截图。
- [Manus web app 官方页](https://manus.im/features/webapp)：说明全栈应用、数据库、登录、Stripe、analytics、domain、rollback、design edit mode。
- [Manus slides 官方页](https://manus.im/tools/nano-banana-pro-slides)：说明生成可编辑 deck、下载 PPTX/PDF/Google Slides。
- [Cloud Computer 帮助页](https://help.manus.im/en/articles/15392111-what-is-the-cloud-computer)：说明持久虚拟机与临时 sandbox 的差别。

## 2. Genspark

### 用户实际体验记录

| 维度 | 记录 |
| --- | --- |
| 触发场景 | 官网是 all-in-one AI workspace，工具入口很多：dashboard、website、presentation、spreadsheet、database、diagram、flowchart 等。用户多半显式选择工具或从一个任务 prompt 开始。 |
| 出现位置 | Genspark Build 官方页直接描述三栏工作区：左侧 chat，中间 live preview，右侧 files。Dashboard、Spreadsheet、Presentation 页面都把富回答当作独立工作产物，不只是聊天消息。 |
| 具体形态 | live dashboard、KPI cards、charts、activity feeds、filters、HTML/CSS/JS 网站、Flutter app、slide deck、spreadsheet、pivot chart、数据表、PDF/Excel/Word/PPT 导入结果。 |
| 可互动能力 | Dashboard 可点数字、看 activity feeds、filters、share role-based access。Website builder 可 hover 测试动画、看 responsive breakpoints、选中 canvas 元素 inline edit、下载代码、Cloudflare Pages 发布。Spreadsheet 每个 cell 可编辑，公式可见，可导出 `.xlsx`、live link、转 Slides。Presentation 可先审 outline，再生成；可点击文本/图片/布局让 AI 改，也可像 PowerPoint 手动编辑并导出。 |
| 生成中体验 | Genspark 的强项是把过程写出来：网站页展示“Drafting files / Writing files / Preview / Files”；幻灯页强调 AI 先问 audience/tone/slide count，先等用户批准 outline，再生成 slides；表格页展示搜索、建 schema、填 rows、插 chart 的 checklist。 |
| 完成后体验 | 完成物是“可继续工作的文件/页面”：dashboard live refresh，网站可发 public URL，spreadsheet 可导出 `.xlsx`，presentation 可导出 PPT/PDF/Google Slides 并分享项目过程。 |
| 错误/不支持体验 | 官网没有集中错误态文档；但 website builder 文案强调模糊时 AI 会问，而不是猜。Spreadsheet 页面强调可见公式和可编辑 cell，降低黑箱感。 |
| 自然/聪明细节 | “先 outline 再 slides”很适合学习场景：先让用户确认结构，再生成重产物。Spreadsheet 的每步 checklist、公式可见、数据源可刷新，也适合魏碑做“可解释学习计算器”。 |
| 生硬/打断风险 | 工具入口过多，容易从“一个回答”跳到“完整工作台”。魏碑不能让每个知识问答都变成外部工作流。 |

### 技术只作为解释

Genspark 的富回答像“多个专门工具拼成的 workspace”：每类产物都有自己的编辑器和预览表面。技术解释可以落到工具路由、文件生成、数据连接和托管发布；但用户感知是“我描述需求，系统给我一个能打开、能改、能分享的东西”。

### 一手证据

- [Genspark 首页](https://www.genspark.ai/)：列出 AI Dashboard、AI Website、AI Presentation、AI Spreadsheet 等工具。
- [AI Dashboard Generator](https://www.genspark.ai/tools/ai-dashboard-generator)：说明 KPI cards、charts、live refresh、filters、role-based access。
- [AI Website Builder](https://www.genspark.ai/tools/ai-website-builder)：说明 chat-left / live-preview-middle / files-right、Cloudflare Pages、inline edit、Flutter target。
- [AI Presentation Maker](https://www.genspark.ai/tools/ai-presentation-maker)：说明 Guide mode、outline approval、slide edit/export/share/fact check。
- [AI Spreadsheet Generator](https://www.genspark.ai/tools/ai-spreadsheet-generator)：说明 cell-native interface、web search、formulas、charts、`.xlsx` export、turn into Slides。

## 3. Replit Agent

### 用户实际体验记录

| 维度 | 记录 |
| --- | --- |
| 触发场景 | 用户在 Project Editor 里直接聊天，描述 app、问题、research topic，或从 connected services 拉数据；也可选择 web app、mobile app、slides、design、data visualization 等 project type。若用户已描述目标，Agent 会自动判断 setup。 |
| 出现位置 | 主要在 Replit Project Editor：chat 与项目编辑器、Preview、Canvas、文件、工具共存。Canvas 是 design view，Preview 是可交互 live app。 |
| 具体形态 | web apps、mobile apps、data dashboards、AI tools、visual designs/prototypes、slides、videos、CSV/PDF/PowerPoint/Markdown docs、connected-service query results。 |
| 可互动能力 | Preview 可直接操作 app、看 responsive sizes、新 tab、devtools、console、DOM、network、storage。Canvas 可移动/resize frames、生成 variants、inline refine、reimagine、build design frame into live artifact；chat 可继续迭代；Agent 会建 checkpoints，可 rollback。 |
| 生成中体验 | Agent 不是只答文字：它 plans、sets up project、creates applications、checks work、fixes problems。Plan mode 可先列任务，用户 Accept tasks 或 Revise plan 后再 build。 |
| 完成后体验 | 用户可以继续 chat refine，再 publish；多个 artifacts 可在同一 project 里共用 backend。 |
| 错误/不支持体验 | 官方 FAQ 说 Agent 会测试自己的 work，并创建 checkpoints；用户可以回滚或继续描述问题让 Agent 修复。Preview 内置 devtools 把故障暴露给用户。 |
| 自然/聪明细节 | Canvas 把“设计草稿”和“live artifact”分清楚：设计 frame 不直接碰 live app，Build 才变成 artifact。这对魏碑非常关键：临时学习 aid 应先是可丢弃草稿，用户确认后才保存进笔记/课程。 |
| 生硬/打断风险 | Replit 是完整 IDE/workspace，学习产品直接照搬会过重。魏碑只需要借“正文旁边的 aid surface”和“临时草稿 → 可保存 artifact”的边界。 |

### 技术只作为解释

Replit Agent 的富回答来自一个完整在线开发环境：Project Editor、Preview、Canvas、checkpoints、publish、backend。技术上是代码与运行时一体；用户体验上是“聊天提出目标，旁边出现可运行/可编辑的项目空间”。

- [Replit Agent 概览](https://docs.replit.com/features/agent/overview)：说明 chat、自动 setup、project types、Plan mode、multi-artifacts、checkpoints。
- [Replit Canvas](https://docs.replit.com/features/design/canvas)：说明 infinite board、frames、artifacts/designs、Generate/Refine/Reimagine/Build、chat snapshots。
- [Replit Preview](https://docs.replit.com/features/editor/preview)：说明 live web view、responsive testing、devtools、new tab、console/DOM/network/storage。

## 4. Vercel v0

### 用户实际体验记录

| 维度 | 记录 |
| --- | --- |
| 触发场景 | 用户用 prompt 创建 live prototypes、full-stack apps、UI、dashboard、ecommerce、AI app，也可上传 screenshots/files、Figma。v0 是显式 prompt 驱动，也会用 agentic features 做 search、browser use、terminal、error fixing。 |
| 出现位置 | v0 的核心是 chat + live preview + code/project version。富回答通常不是消息内图表，而是一个可运行 app/component preview，并可进入 Design mode。 |
| 具体形态 | high-fidelity UI、React/Next.js code、full-stack app、dashboard、data visualization code、interactive components、visual explanations、forms、chatbot、knowledge base 等。 |
| 可互动能力 | Design mode 可在 live preview 上选择元素、调 typography/color/background/layout/border/radius/shadow/content，也可对选中元素写自然语言指令；pending edits 可 undo/redo/reset/before-after preview；Apply 后变成新版本，diffable/revertable。Sharing 可 view/edit/duplicate。版本可恢复，部署使用 latest version。 |
| 生成中体验 | v0 文档强调 real-time preview、visual progress indicators、rich UI feedback for agent actions。上传截图时，v0 会分析 layout/colors/components/functionality 并生成 code。 |
| 完成后体验 | 用户可一键 deploy 到 Vercel，或开 pull request；可分享 chat history 与 generated components，团队可 view/edit/duplicate 独立迭代。 |
| 错误/不支持体验 | 官方 docs 明确 Design mode 只在 latest preview runtime、latest chat version 可用，不支持 read-only chats 或 mobile viewports。技术动作能变成版本，便于 revert。 |
| 自然/聪明细节 | Design mode 的“选中真实预览里的元素 → 改样式 → 先 pending → Apply 生成版本”非常自然，因为用户不需要描述坐标；同时保留版本边界。 |
| 生硬/打断风险 | v0 的富回答默认是代码/app 产物；对魏碑要压缩成局部学习 aid，不应要求用户理解 code、deploy、PR。 |

### 技术只作为解释

v0 的技术解释是：chat 输出真实代码，preview runtime 运行它，Design mode 把视觉调整序列化回 chat，再生成新 version。用户感知则是“我在结果上点一下，直接让 AI 改这一块”。

- [v0 是什么](https://v0.app/docs)：说明 full-stack apps/live prototypes、one-click deploy、real-time preview、rich UI feedback。
- [Screenshots and Files](https://v0.app/docs/screenshots)：说明拖入文件/截图生成高保真 UI 和代码。
- [Design mode](https://v0.app/docs/design-mode)：说明 live preview 选元素、视觉面板、自然语言局部指令、pending edits、Apply 成新版本。
- [Versions](https://v0.app/docs/versions)：说明每次 message 更新代码块会创建版本，可 restore。
- [Sharing](https://v0.app/docs/sharing)：说明 chat 分享、view/edit、duplicate workflow。

## 6. Bolt

### 用户实际体验记录

| 维度 | 记录 |
| --- | --- |
| 触发场景 | 首页就是 prompt box：“What will you build today?” 用户可以 Build now，也可以 Plan；还可选择 Website、Slides、Prototype，或从 Figma/GitHub import。 |
| 出现位置 | Bolt 在浏览器里运行完整构建空间：chat、preview、files/code view、database/settings、publish 等。 |
| 具体形态 | websites、web apps、mobile apps、slides/prototypes、full-stack app、database/auth、published site、code files。 |
| 可互动能力 | 用户可在 Preview window 试 app；用 selector tool 点页面元素并让 Bolt 改；Version History restore；Code View 查看/编辑/创建/删除文件；target/lock files、highlight code ask Bolt；Publish 后在 chat 中拿到链接。Plan Mode 可继续讨论，也可点 quick action 实施。 |
| 生成中体验 | QuickStart 明确“wait around five minutes while Bolt creates your app”，有数据库会更慢。首页强调自动测试、重构、迭代来减少错误。Plan Mode 可在首页第一 prompt 就开启：先产出计划，用户 refine 后再 Build。 |
| 完成后体验 | 可 publish 到 built-in hosting，免费 `bolt.host` 子域名；项目代码归用户，可连接 GitHub，Bolt Cloud 内置数据库/hosting/domains。 |
| 错误/不支持体验 | QuickStart 直接说如果 favorites 不立即显示，尝试 logout/login；Code View 警告直接改代码容易 break，Version history 不覆盖 code view 修改，出错需 prompt Bolt 修。帮助中心有 troubleshooting 和 paid/free support 边界。 |
| 自然/聪明细节 | Plan / Build now 并列，让用户一开始就能选“先想清楚”还是“直接做”；selector tool 点中具体元素再 prompt 很适合局部改动。 |
| 生硬/打断风险 | token usage 在体验里很显眼；学习回答若暴露太多成本/构建等待，会打断理解。魏碑应隐藏资源消耗，只在需要时说明。 |

### 技术只作为解释

Bolt 的富回答依赖 browser 内运行环境、文件系统、preview、数据库与 hosting。技术优势来自 WebContainers/云能力；用户感知是“聊天 + 预览 + 代码/版本/发布”。

### 一手证据

## 8. ChatGPT 与 Codex

### 用户实际体验记录

ChatGPT 不是给所有问题套同一种富回答，而是把不同重量的任务分配到不同表面。

| 能力 | 怎么触发 | 出现在哪里 | 用户能做什么 | 体验判断 |
| --- | --- | --- | --- | --- |
| 数据分析 | 上传数据或直接要求分析；模型也会在结构化视图更有帮助时生成 | 回答内表格、静态或交互图，必要时可展开 | 悬停、切换图表、下载、继续追问、要求换算法或分组 | 最接近“正文自然长出一个工具”，因为图表直接服务当前结论 |
| 图片生成与编辑 | 用户明确要求生成/修改图片 | 消息内图片与独立图片编辑器 | 局部选择、继续修改、撤销重做、分享 | 富回答不再是解释图片，而是直接交付并继续编辑视觉对象 |
| Canvas | 模型判断长文/代码需要工作面，或用户说“用画布” | 聊天旁边的独立编辑面 | 直接编辑、选中局部让模型改、看版本、预览 HTML/React、运行 Python | 适合中型持续任务；把长产物从聊天滚动中移开 |
| Apps / MCP Apps | 用户点名应用、连接服务，或模型调用有界工具 | 消息内卡片、全屏、画中画 | 点击、选择、填写、调用外部动作、继续对话 | 同一个富对象可根据任务重量改变占用空间 |
| Visualize | 用户显式 `@Visualize`，模型也可在视觉更有帮助时选择 | 对话中的图表、地图、流程图、计算器、模拟器、交互讲解器 | 拖滑块、移动探针、暂停、重启、调参数 | 它把“画图”升级为“操纵对象以理解关系” |
| Sites | 用户要求建立网站/应用或从工作成果发布 | 独立、持久、可分享的站点 | 预览、修改、保存版本、部署、控制权限 | 只有明确需要持久化时才升级，不应作为普通回答默认形态 |
| Codex | 用户发起工程任务 | 任务工作台中的计划、代码差异、终端、浏览器预览、批注和 PR | 审批、改方向、看运行结果、标页面、审查改动 | 这不是“更富的聊天”，而是围绕真实动作组织的执行表面 |

### 最值得学的体验规则

OpenAI 的官方界面指南明确区分 inline、fullscreen 与 picture-in-picture。消息内卡片要简短、行动少、避免嵌套滚动；全屏仍保留输入框；持续直播类任务才适合画中画。官方体验原则还强调：只在 UI 真正有帮助时生成，不把对话变成导航菜单，也不为了装饰而加组件。

这意味着“富回答”不是由组件类型先决定，而是先判断：

1. 用户只需看一眼，还是需要操作？
2. 操作只需一次，还是要持续修改？
3. 结果是临时解释，还是要变成持久成果？
4. 当前表面装得下吗，还是应该升级到侧边/全屏？

## 9. Claude

### 用户实际体验记录

Claude 有两条明显不同的富回答路径：

| 路径 | 用户看到什么 | 怎么互动 | 适合什么 |
| --- | --- | --- | --- |
| Visual / Interactive Content | 回答中直接出现天气、食谱、图表、流程图、选择题、排序等视觉内容 | 点选、切换、调整份量/单位、继续追问 | 轻量、与当前问题紧密相连的解释 |
| Artifacts | 右侧独立窗口里出现文档、代码、HTML、SVG、React 应用 | 直接编辑、选中局部修改、看源码、切版本、复制、下载、分享、发布 | 需要继续维护的中重型产物 |

Claude 的关键不是“Artifact 很强”，而是它把选择标准说得很清楚：当内容独立、可复用、足够长，或需要运行/编辑时才离开聊天。错误也不只显示报错文本，Artifact 可以出现“让 Claude 尝试修复”的下一步。

体验上的优点是：正文和产物分开，用户仍然能继续说话；产物本身可编辑，不必每次整段重生。风险是平台和端能力不一致，部分视觉内容在移动端会降级成文本，自定义交互仍处于受限范围。

## 10. Gemini 与 NotebookLM

### Gemini：显式进入创作面

Gemini Canvas 的体验更偏“用户先选择进入工作区”。聊天在左，文档、应用、代码、幻灯、测验、信息图或网页在右。用户可以直接改内容，选中局部再问 Gemini，看控制台和错误，切换版本并分享或导出。

Gemini 还把富回答扩展到音频、故事书、图像、视频、引导式学习、闪卡和测验。这些形态通常有明确入口和专门播放器/翻页/练习表面，优点是用户知道自己进入了什么模式；缺点是入口较多，能力受账号、地区、年龄和设备限制时容易碎片化。

### NotebookLM：围绕资料源的学习产物工厂

NotebookLM 和普通聊天助手的区别更大：用户先建立资料集合，聊天负责提问，Studio 负责把资料转成不同学习产物。

| 产物 | 用户看到什么 | 能做什么 | 学习价值 |
| --- | --- | --- | --- |
| Audio Overview | 围绕资料的主持人式音频讨论 | 后台生成、调格式/长度/语言、播放、下载、分享，部分模式可语音加入 | 把阅读材料变成可听解释 |
| Video Overview | 解释型或短视频 | 播放、快进、全屏、分享 | 用视听结构重组材料 |
| Mind Map | 可展开折叠的脑图 | 缩放、点节点向聊天追问、下载 | 从全局结构进入局部问题 |
| Flashcards / Quizzes | 闪卡与测验面板 | 调难度和数量、提示、错题复练、进度、全屏、下载 | 直接服务复习与自测 |
| Infographic / Slide Deck | 信息图或演示文稿 | 后台生成、缩放、下载、分享、逐页修改 | 把材料变成展示和回顾对象 |

NotebookLM 的强点不是“形态多”，而是多数产物都继承同一资料边界。失败时官方也明确提醒内容可能不准确、资料中没有答案或生成会耗时。它最接近魏碑的学习场景，但其 Studio 更像一个产物栏；魏碑仍需解决“某一次疑惑如何自然长出一个小工具”，不能直接照搬整套工厂。

- [Gemini Canvas](https://support.google.com/gemini/answer/16047321?hl=en)：说明左右分栏、直接编辑、局部提问、代码控制台、版本、分享与导出。

## 11. Microsoft Copilot、Perplexity、Grok 与 Mistral

### Microsoft Copilot：回答落进用户本来工作的地方

Copilot Pages 把聊天里的临时内容转成可编辑、可追加、可分享、可多人协作的持久画布；Excel、PowerPoint、Word、Teams、Outlook 则把富回答直接放进用户原有工作表面。它最自然的地方是：图表去 Excel，演示去 PowerPoint，文稿去 Word，而不是每次发明一个新容器。

这条路线对魏碑的启发是“学习工具也应回到学习场景”：原文批注贴着原文，函数实验贴着公式，证据板贴着材料引用，而不是都塞进同一张通用卡片。

### Perplexity：来源先在场，再升级产物

Perplexity 的稳定优势是回答默认伴随来源。官方开发者文档还确认复杂代理任务可以后台执行、取消、生成文件、在沙箱中运行代码，并交付图表、PDF 或交互仪表盘类结果。

但本轮其部分产品介绍页受到访问限制，因此“Pages/Labs 等前台具体布局”不作为已验证事实。能确认的是它把来源化搜索答案作为底座，再把重任务升级为研究或文件产物。

一手证据：[Perplexity API Overview](https://docs.perplexity.ai/docs/getting-started/overview)、[Search API](https://docs.perplexity.ai/docs/search/quickstart)、[官方文档索引](https://docs.perplexity.ai/llms.txt)。

### Grok：用模式入口告诉用户“现在要做什么”

Grok 将 Think、DeepSearch、Imagine、Build 拆成显式模式。Build 是全屏终端代理，用户能看计划、审批、沙箱执行和子代理；Imagine 负责图像和视频；DeepSearch 负责搜索报告。优点是模式感清晰，缺点是不同能力容易割裂成几套产品面。

一手证据：[Grok 3](https://x.ai/news/grok-3)、[Grok Build](https://x.ai/cli)、[Build 文档](https://docs.x.ai/build/overview)、[Imagine](https://docs.x.ai/developers/model-capabilities/imagine)。

### Mistral Le Chat：可信来源与权限也属于富回答

Mistral 官方材料更强调企业搜索、文档库、连接器、权限和 Agent builder，而不是独立视觉画布。它说明“富”不只意味着图形和互动，也可以是答案能追溯到企业资料、继承访问控制并继续执行任务。本轮没有找到足够一手证据证明其前台已有与 Canvas/Artifacts 同等级的通用可视化工作面，因此不作此结论。

一手证据：[Le Chat Enterprise](https://mistral.ai/news/le-chat-enterprise/)。

## 12. 富回答的体验形态谱系

下面这张表比“有多少组件”更重要。它描述用户到底在完成什么动作。

| 用户此刻需要 | 最小合适形态 | 不该出现什么 | 典型例子 |
| --- | --- | --- | --- |
| 快速理解一个结论 | 正文 + 一张小图/表/批注 | 全屏工作台、长加载 | 定义对照、小趋势图、原文高亮 |
| 比较多个对象 | 可排序/切换的比较面 | 重复一遍静态正文 | 比较矩阵、方案切换、光谱位置 |
| 观察变量关系 | 可调参数实验 | 只有一张不可操作截图 | 函数曲线、物理变量、经济情境 |
| 验证自己是否理解 | 一次小测/揭晓/步骤核对 | 把练习包装成大型游戏 | 测验、闪卡、排序、预测后验证 |
| 追踪证据和推理 | 可点击来源的证据结构 | 无来源关系图 | 论证图、证据板、推导步骤 |
| 持续修改一个成果 | 侧边画布 | 在聊天里反复贴整段新版本 | 文档、代码、视觉方案、长图表 |
| 完成长时间任务 | 任务工作台 | 静默等待、只给最终成品 | 研究、数据清洗、应用生成 |
| 保存、分享或复用 | 持久产物 | 默认把所有临时解释写入笔记 | 页面、文件、站点、学习卡 |

由此可见，富回答不是“文本 / 非文本”二选一，而是逐级增强：

`纯文字 → 轻量内嵌 → 可操作内嵌 → 侧边画布 → 全屏任务 → 持久产物`

系统真正需要学习的是**什么时候升级、升级到哪一级、什么时候保持克制**。

## 13. 谁决定采用什么形态

竞品给出的答案不是“全由 Agent 决定”或“全由用户选择”，而是两层控制：

| 决定者 | 应负责什么 | 用户感受 |
| --- | --- | --- |
| Agent | 读懂问题、材料形状和学习动作，默认选择最小有效形态 | 不需要先学会一堆工具名 |
| 用户 | 明确要求、否决、替换或升级形态 | 随时说“只讲文字”“画图”“换成交互”“别保存” |
| 产品界面 | 展示当前形态、提供轻量切换和失败退路 | 不被模型的错误选择绑架 |

合理的优先级应当是：

1. 用户明确要求优先。
2. 没有明确要求时，Agent 选择最小有效形态。
3. 证据不足、渲染不支持或生成成本过高时，诚实降级。
4. 用户可在结果上直接切换，不必重新组织整句问题。

未来可以增加显式开关，但不应把它设计成唯一入口。更实用的是结果级控制：`改用文字`、`画出来`、`展开实验`、`重新生成这一块`、`保存为学习材料`。

## 14. 技术路线只解释体验，不替代体验

主流方案大致有三类，且各有明显代价。

| 路线 | 怎么工作 | 优点 | 风险 | 相关一手资料 |
| --- | --- | --- | --- | --- |
| 原始 HTML / iframe | 模型或工具产出网页，宿主在沙箱 iframe 中展示 | 自由度高，能做复杂实验、媒体和小应用 | 风格不一致、双滚动、性能、安全、焦点与无障碍更难 | [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview)、[OpenAI Apps SDK UI](https://developers.openai.com/apps-sdk/build/chatgpt-ui) |
| 声明式结构 + 本地组件 | 模型输出受约束 JSON，宿主用可信组件库原生渲染 | 稳定、安全、统一、易做流式与移动适配 | 受组件目录限制，复杂新形态需要前端补能力 | [A2UI 介绍](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)、[json-render](https://json-render.dev/docs) |
| 混合模式 | 常见形态走本地组件，特殊实验才进沙箱 HTML | 在一致性与创造力之间平衡 | 需要清楚的升级规则与两套验证链路 | [A2UI 与 MCP Apps 对比](https://developers.googleblog.com/a2ui-and-mcp-apps/) |

另外两类基础设施解决不同问题：

- [Vercel AI SDK 的生成式界面](https://vercel.com/blog/ai-sdk-3-generative-ui) 与 [多步生成式界面教程](https://vercel.com/academy/ai-sdk/multi-step-and-generative-ui) 说明如何把模型工具调用映射为 React 组件，并给加载、成功、错误提供不同 UI。
- [AG-UI](https://docs.ag-ui.com/) 提供运行生命周期、文本、工具、状态和错误事件流，适合支撑生成进度、调试、重试和双向互动；它本身不决定视觉长什么样。

这轮研究后的技术结论已经进一步收敛：**魏碑应让本地网页运行时承担主要富回答显示，但默认由受控声明式程序驱动，不让模型直接执行任意网页代码；SwiftUI 负责可信宿主、来源、位置、安全与降级。** OpenUI 的协议、流式解析和状态机制值得借用，默认通用卡片视觉不适合直接搬入魏碑。具体决策见《富回答网页主运行时决策》。

## 15. Pi 生态能做什么，不能替魏碑做什么

### 已确认能力

Pi 扩展可以注册工具、命令、渲染器和终端界面。第三方扩展也已经有人做过：生成 HTML/SVG/Canvas/Chart.js 后打开独立原生窗口或浏览器，生成长回答网页，或把关系图输出成自包含 HTML。

### 关键限制

魏碑当前通过 RPC 把 Pi 当作内嵌 Agent 层。Pi 官方 RPC 文档明确说明，部分终端专用 UI 在 RPC 模式没有宿主界面可用，`ctx.ui.custom()` 会返回空，若干 TUI 方法会退化为无操作。也就是说：

> Pi 可以帮助模型决定和生成富回答，但不能凭一个 TUI 插件自动把高质量交互界面嵌进魏碑。

第三方生成式 UI 扩展多半打开外部窗口或浏览器，这能证明“Pi 能生成”，却不能解决“魏碑里怎么自然显示、怎么跟材料跳转、怎么适配宽度、怎么不卡顿、怎么调试”的产品问题。

### 对魏碑的实际含义

| 层 | Pi 负责 | 魏碑 App 负责 |
| --- | --- | --- |
| 判断 | 是否需要富回答、需要哪种学习动作 | 给用户覆盖和切换入口 |
| 生成 | 输出结构化内容、参数、来源、状态或受控网页请求 | 校验协议、拒绝危险内容、选择显示表面 |
| 运行 | 调用工具、补数据、继续推理 | 渲染、交互、性能、错误、流式状态、可访问性 |
| 反馈 | 读取用户在组件中的动作并继续回答 | 把动作可靠传回 Pi，并管理临时/持久状态 |

一手证据：[Pi Extensions](https://pi.dev/docs/latest/extensions)、[Pi RPC](https://pi.dev/docs/latest/rpc)、[Pi Generative UI 扩展](https://pi.dev/packages/%40ryan_nookpi/pi-extension-generative-ui)、[Pi HTML Long Answer](https://pi.dev/packages/pi-html-long-answer-extension?page=58)、[Pi Graph Viz](https://pi.dev/packages/pi-graph-viz)。

## 16. 旧版魏碑到底做到哪一步

### 结论

**旧版不是毫无实现，但它也不是用户当时能稳定触发的正式能力。准确说，它是救援分支里的“已接线原型 + 硬编码视觉验收场景”。**

| 检查面 | 已确认事实 | 判断 |
| --- | --- | --- |
| 当前版本 | 当前检出 `v0.1.0` / `f1c08d82`，不存在旧解析器、样式和互动学习技能 | 当前用户无法触发旧富回答 |
| 历史实现 | 救援提交 `e86dc2d3` 曾加入 `weibei-interactive` 声明式 JSON、解析器、WebKit 渲染、样式、自检和技能 | 代码层曾真实接线，不只是设计稿 |
| 形态数量 | 历史技能列出 28 种 `kind`，覆盖测验、图表、函数、文本、关系、证据、算法、语言、艺术和空间等 | 能力面很宽，但过早被组件清单主导 |
| Agent 判断 | 历史技能要求模型先判断学习动作、证据形状、是否需要动手，再选择一个最小主互动；简单问题保持纯文字 | 判断方向正确，规则也比“逢问必画”成熟 |
| 安全 | 禁止任意 HTML/SVG/JS/CSS/URL，只允许受控 JSON 和白名单数据边界 | 安全与稳定方向正确 |
| 截图 | `agent-interactive-gallery-*` 场景在 App 内直接注入固定消息与 JSON，并强制离线 | 截图证明渲染器能画，不证明 Pi 会真实生成 |
| 真实 Pi | 当时真实回答回路运行约 11 分钟仍未完成，整体状态被明确记为“未通过” | 端到端没有验收完成 |

### 旧版方向为什么大体正确

1. 它已经意识到不能只给文本，允许回答里出现一个主研习面。
2. 它没有让模型直接写任意网页，而是使用安全声明式协议。
3. 它规定正文不要和组件重复，并把来源合并到回答附件。
4. 它尝试跨学科，而不是只做图表或选择题。
5. 它考虑了深色模式、窄宽度、键盘焦点、减少动效和来源跳转。

### 为什么实际观感仍在及格线以下

本轮重新查看了本机保留的三张旧验收截图，并结合历史代码复核，问题不是“颜色还差一点”，而是产品表面没有真正分层：

| 问题 | 用户实际感受 | 根因 |
| --- | --- | --- |
| 所有东西都挤进一张超宽长回答页 | 复杂实验、关系图、练习都像报告附件，阅读距离很长 | 只有一种消息内表面，没有 inline/side/fullscreen 选择 |
| 视觉主要靠横线、边框、色块和栏目 | 看起来像排版样张或组件画廊，不像为当前问题专门长出的工具 | 28 类被统一套进少数通用版式语言 |
| 留白和信息密度失衡 | 轻内容显得空，重内容又挤；明暗主题表现不稳定 | 固定大宽度与统一卡片尺度没有按任务调整 |
| 互动只在“最终态”可见 | 用户看不到正在生成、部分完成、失败、修复和继续修改 | 协议只关注最终 JSON，没有完整生命周期 |
| 来源卡与主任务割裂 | 用户知道有来源，却不清楚哪个结论或交互状态对应哪段材料 | 来源主要集中在底部附件，而非贴近证据点 |
| 点击后反馈弱 | 操作状态只暂存在内存，主要影响下一问，不自动形成即时解释 | 组件动作与 Agent 回合没有形成清晰闭环 |
| 错误会暴露原始协议 | JSON 错误或不支持类型时像“系统坏了” | 缺少用户可读降级、重试和调试表面 |
| 截图与真实能力脱节 | 画面看起来完成，用户却从未亲自触发 | 视觉验收使用硬编码离线消息，真实 Pi 链路未通过 |

所以旧版最值得保留的不是 28 个组件，也不是那套 CSS，而是三个原则：**模型自主选择、结构化安全协议、正文与来源不重复。** 最需要推倒重想的是：**表面分级、生成生命周期、局部修改、真实端到端触发，以及每种学科工具真正的操作逻辑。**

## 横向体验规律

| 体验问题 | 成熟产品的共同答案 | 对魏碑的讨论结论 |
| --- | --- | --- |
| 谁决定富回答？ | 自动判断与显式入口并存；用户可以随时覆盖 | 默认让 Agent 判断，但必须提供结果级切换，不能让用户先学组件名 |
| 先选组件还是先看任务？ | 先判断用户动作、任务重量和是否需要操作，再选表面 | 不从“28 种组件里挑一个”开始，而从“用户现在要观察、比较、验证还是创作”开始 |
| 放在哪里？ | 轻内容内嵌，中任务侧边画布，重任务全屏，持久成果独立保存 | 魏碑至少需要表面分级，不能把所有内容塞进同一消息网页 |
| 和正文怎么共存？ | 正文保留结论和对话，富对象承载操作，不重复 | 一两句直接回答 + 一个合适工具 + 就近证据，比“长正文 + 再抄一份卡片”自然 |
| 怎么生成才不生硬？ | 先出现计划/骨架/加载状态，再逐步完成 | 用户要看见正在形成的对象，而不是先露协议源码，最后突然替换 |
| 用户怎么改？ | 点选对象、局部指令、参数控制、版本与撤销 | “改这个变量/这一步/这个区域”必须是一等操作 |
| 失败怎么办？ | 明确错误、可重试、可降级、保留已完成部分 | 不能把非法 JSON 或空白面板丢给用户；文本替代也要说明为什么 |
| 来源怎么放？ | 来源贴近结论和对象，同时保留总览 | 每个关键数据、步骤、区域和判断应能回跳，不只在底部集中列卡片 |
| 临时还是持久？ | 默认临时，用户确认后再保存/分享/发布 | 当前先把富回答当学习辅助，不默认写回笔记；以后再加显式保存开关 |
| 怎么验收？ | 真实任务、真实模型、真实窗口、真实交互和失败测试 | 截图画廊只能验渲染；必须另做真实 Pi 触发、流式、错误、窄宽度和长回答验收 |

## 魏碑讨论底稿

这轮调研还不等于最终设计，但已经能排除两条错误路线：

- **不能只做漂亮 Markdown。** 它解决不了调参、验证、局部操作、持续修改和运行状态。
- **也不能让模型任意吐一个大 HTML 页面。** 它会带来风格漂移、滚动、性能、安全、调试和移动适配问题。

下一轮设计应围绕五个问题展开，而不是继续扩组件清单：

1. **表面分级**：哪些回答留在正文，哪些进入内嵌工具、侧边画布或全屏实验？
2. **Agent 判断**：什么证据足以触发富回答，用户如何显式要求、否决和替换？
3. **表达协议**：哪些高频学习形态使用稳定声明式组件，哪些特殊实验允许隔离 HTML？
4. **完整生命周期**：准备、流式、可操作、失败、重试、降级、局部修改、关闭分别怎么呈现？
5. **真实验收**：怎样证明模型真的会选对、真的生成成功、真的帮助用户，而不是只把测试夹具画出来？

当前可作为共同起点的产品判断是：

> 魏碑的富回答，应当是 Agent 基于当前文档与疑惑，主动选择的“最小有效学习工具”；它与文字解释、材料证据和继续追问连成一个回合。用户可以显式要求或切换形态。默认临时、可丢弃，不急着写回笔记；复杂时再升级为侧边或全屏，特殊形态才使用隔离网页能力。

这个判断保留了旧版正确的三件事——模型自主选择、安全结构化协议、来源可回跳——同时把重点从“有多少组件”转回到“用户到底看见什么、能做什么、失败时怎么办”。
