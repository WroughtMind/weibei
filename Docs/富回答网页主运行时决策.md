# 魏碑富回答网页主运行时决策

状态：主路线已实施，真实模型与全场景验收收尾中
日期：2026-07-18

## 当前实施快照

- 自定义 OpenUI 网页运行时已经承载 T1 高质量深组件；T2 允许集合当前由受控 SwiftUI 渲染器承载，并逐步接入专业渲染能力。两者通过同一透明宿主接入 Agent 回答流，SwiftUI 继续掌握来源、宽度、高度、主题、安全和失败降级。
- 模型不再每轮携带完整组件库，而是先调用 `weibei_ui_catalog`，按本轮学习动作取得 1–3 组相关 T1 签名、T2 允许字段和渲染器适配提示。
- 回答根结构已经从“单张完整页面”改为正文片段与场景片段交替的有序序列；嵌入模式没有页头、导航、调试面板和独立背景。
- T1 深组件继续保留高质量联动；T2 已提供一组受控可组合能力和注册渲染提示，覆盖坐标框架、区域标注、图层、图像、数据集、通用序列、控件、探查和状态绑定，负责没有专属组件的长尾组合。
- 当前只完成了少量真实窗口链路复现，用来修启动、透明背景、动态高度、宽度和截图真实性；此前七题没有逐题原始模型输出与真实窗口截图留档，不能算真实 Pi 通过。完整 56 题首轮仍待按冻结基线重新运行。

专业渲染路线保持开放：OpenUI、ECharts、JSXGraph、Plotly、Python 只是当前候选，不构成固定内核或封闭名单；Python 也不被永久限制为静态计算，只要具体互动方案通过受控适配器满足内联、安全、性能与生命周期要求，就可以进入能力注册表。

## 结论

魏碑富回答应改成 **网页主渲染、原生可信宿主、受控生成协议**：

1. 富回答的主要视觉与交互由本地 HTML、CSS、SVG、Canvas 和必要的 WebGL 承载。
2. Pi 默认不直接自由书写完整网页，而是输出受约束的界面程序；网页运行时把它编译成真正的互动界面。
3. SwiftUI 继续负责对话、材料来源、位置与尺寸、权限、安全、主题、降级和聚焦实验面。
4. OpenUI 值得借用的是语言、流式解析、组件契约、本地状态、增量修改和错误修复；不能照搬它的通用卡片、表格与仪表盘视觉。
5. 魏碑必须建立自己的学习组件库、计算与模拟内核、视觉语法、参考图谱和验收题库。
6. 任意 HTML/JavaScript 作为高自由度试验路线单独验证，不与默认可信主路混在一起。

这不是“原生还是 HTML”的二选一。**HTML 是主要显示介质，受控协议是稳定生成方法，原生 App 是可信边界。**

## 为什么要改变原路线

当前原生底座已经证明协议可以校验、场景可以落进 App、滑杆和步进可以工作，但真实画面也暴露了上限：

- 不同学科仍容易退化成线、框、栏目和文字排布。
- 每增加一种真正不同的视觉或模拟，都要继续扩 SwiftUI 渲染器。
- SVG、Canvas、公式排版、图像叠层、动画和物理模拟在网页运行时更成熟、组合成本更低。
- 原生组件可以统一风格，却很难快速获得足够宽的生成式表达空间。

因此当前 SwiftUI 生成渲染器保留为协议验证、轻量原生场景和失败降级，不再承担全部富回答的视觉上限。

## OpenUI 实际验证后的判断

本轮不只阅读文档，也在 OpenUI Playground 输入了一条真实学习任务：要求生成一次函数 `y = mx + b` 的互动解释，包含坐标图、两个滑杆、实时公式和简短结论。

得到的结果说明两件事：

### 值得借

- 模型输出紧凑、逐行、可解析的界面程序，而不是冗长 JSON。
- 组件库、Prompt 和渲染器来自同一个契约，能降低前后端漂移。
- 页面可以边生成边出现结构。
- 本地状态、动作、工具调用、增量补丁和结构化错误已经形成完整机制。
- 官方仓库已有 Pi Agent Harness，证明 Pi 可以注入同一份组件 Prompt 并把输出流交给网页渲染器。

### 不能照搬

- 默认学习结果仍是标题、两张卡片、折线图、控件卡和提示卡，产品语言偏仪表盘。
- 模型生成了滑杆，但滑杆变化后，图表和“当前公式”没有同步变化；它只改变了控件状态。
- 默认组件名与示例会强烈诱导模型使用卡片、标签、表格和通用图表。
- 通用组件解决“能拼界面”，不能自动解决“知识关系是否被正确模拟”。

所以魏碑不能只给 OpenUI 换一套颜色。必须把**知识计算、状态变化和视觉表达封进更深的学习组件**，让模型描述意图和参数，而不是临时手写一堆互不联动的通用控件。

## 魏碑自己的四层系统

### 第一层：原生可信宿主

SwiftUI 只掌握 App 级能力：

- 富回答放在正文、展开研习面还是聚焦实验面。
- 当前材料、证据编号、来源回跳和图片资产。
- 高度、宽度、外层滚动、键盘焦点和深浅主题。
- 是否允许打开来源、继续追问或进入更大实验面。
- 运行超时、内存预算、失败提示和文字降级。

网页不能获得笔记写入、任意文件、外部网络、剪贴板或通用 App 命令。

### 第二层：魏碑网页运行时

本地打包一个专用运行时：

- HTML 负责语义结构和可访问性。
- CSS 负责魏碑的纸墨材质、排版、密度与响应式布局。
- SVG 负责函数、关系、几何、时间、标注和矢量叠层。
- Canvas 负责高频动画、粒子、实验和大数据点。
- WebGL 只在三维、复杂场或性能确实需要时启用。
- KaTeX、Mermaid 或其他库只作为内部实现，不直接成为模型必须学习的产品概念。

所有依赖随 App 本地打包；运行时默认无外部网络、无远程字体、无第三方脚本。

### 第三层：魏碑学习组件库

组件不能只是一组按钮、卡片和图表。它分成三类：

| 层级 | 作用 | 例子 |
| --- | --- | --- |
| 视觉对象 | 可组合的最小知识呈现对象 | 文本片段、公式、标尺、控制对象、路线、区域、图片层、标签、探针 |
| 能力内核 | 保证互动与计算真的正确 | 函数采样、单位换算、公式求值、状态机、时间插值、图像坐标、力矢量、守恒检查 |
| 学习构型 | 一类认知动作的成熟组合 | 参数探索、逐步推导、原文边注、因果追踪、图像观察、方案比较、数据刷选 |

能力内核必须是“深组件”：例如模型给出表达式、参数范围和解释目标，函数探索器自己完成采样、坐标、滑杆联动和异常处理；不能让模型分别生成一个滑杆、一张静态折线图和一行假装实时的公式。

### 第四层：Pi 表达与参考系统

Pi 每次只得到与当前问题相关的一小组能力和参考：

1. 先判断纯文字是否已经足够。
2. 识别用户要观察、比较、操控、推导、定位、追踪、验证还是练习。
3. 根据证据形状选择 1–3 个组件组。
4. 从持续增长的参考库中检索 2–4 个最相关的高质量参考和反例。
5. 生成受控界面程序；目录直接附带枚举、数值范围和数组长度约束，不让模型靠猜参数。
6. 结构、证据和预算校验尽量一次批量返回完整诊断；最多提交三次，第三次仍失败就保留正文。

不能把所有组件和几十个例子永久塞进系统 Prompt。组件越多，模型越容易混淆；参考越多，模型越容易机械模仿。参考必须按当前任务动态检索。

这条链路已经落成 `weibei_ui_catalog` 工具：Pi 先提交学习动作、知识形状、来源媒介、主互动和表面重量，工具再返回当前允许的 1–3 个组件组、精确签名、T2 允许字段、渲染器适配提示、反模式和运行预算。随后 Pi 才能调用 `weibei_rich_answer` 提交界面程序；T1 使用目录返回的白名单，目录不匹配时必须重新选择。完整组件库与参考库持续增长，存在于本地渲染器里；模型每回合只看见与当前问题相关的子集，而不是被少数固定样例封顶。

```text
用户问题 + 当前材料
→ Pi 判断纯文字或富回答
→ weibei_ui_catalog(学习动作, 知识形状, 主互动, 表面)
→ 返回相关组件签名 + 高质量参考 + 反例 + 预算
→ Pi 生成受控界面程序
→ weibei_rich_answer(表达方案, 程序, 证据)
→ 校验、渲染、最多两轮定向修复或文字降级
```

## 参考不是模板

魏碑应准备很多参考，但每份参考解决的是“怎样思考和组合”，不是让模型照抄一张固定页面。

每份参考包含：

- 适用的学习动作与证据形状。
- 不适用条件。
- 最小必要对象与唯一主互动。
- 为什么用这种视觉，而不是表格、流程图或纯文字。
- 一份可运行界面程序。
- 一张经过验收的截图。
- 常见失败和反例。

参考索引不按学科死分，而按以下维度交叉检索：

| 维度 | 例子 |
| --- | --- |
| 学习动作 | 观察、比较、推导、试验、定位、追踪、验证、练习 |
| 知识形状 | 连续量、离散状态、时间、空间、关系、文本、图像、公式 |
| 来源媒介 | PDF 原文、网页、图片、表格、代码、地图 |
| 主互动 | 拖动、切换、步进、缩放、叠层、筛选、排序、标注 |
| 表面重量 | 正文内、展开面、聚焦实验面 |
| 证据状态 | 完整、局部、冲突、截断、无法确认 |

这样同一个“调节并观察变化”的参考可以服务数学函数、物理运动、金融敏感性和生物过程，而不会把学科变成固定皮肤。

## 统一风格如何不变成同一张卡片

魏碑统一的是规则，不是版式：

- 统一字体、纸墨色、朱砂焦点、来源蓝、成功绿和错误语义。
- 统一控件尺寸、键盘行为、动效节奏、来源行为和失败语言。
- 统一答案与材料的关系：先给结论，工具承载操作，来源贴近关键对象。
- 禁止网页导航、Hero、营销结构、功能卡片墙和装饰性指标。

差异必须来自知识本身：

- 文本精读从原文边缘长出批注，不套图表卡片。
- 函数让坐标与探针成为主画布，不再附一排静态指标。
- 生物和化学使用对象、区域、粒子、状态和守恒，不退化成几根连线。
- 图像与设计让原图占主要面积，比例线、焦点和测量覆盖在图上。
- 历史与金融把事件、证据和量化变化放进同一时间语境，而不是普通仪表盘。

## 默认协议不等于任意 HTML

当前生成协议统一为 v2：模型只能在每个场景中二选一提交 T1 深组件程序或 T2 受控渲染计划。引擎对 v1 的兼容仅用于读取早期已保存的本机历史消息，不是新生成的备用路径。

“HTML 效果最好”与“让模型自由执行任意网页代码”是两件事。

### 默认主路

- 模型输出 OpenUI Lang 或同等级的受控声明式程序。
- 只能调用魏碑注册的组件和确定性能力内核。
- 模型不能提供网络地址、脚本地址、字体、任意 CSS、任意 DOM 事件或 App 桥名称。
- 运行时可以生成丰富 HTML/SVG/Canvas，但代码由魏碑掌握。

### 高自由度试验路

另一条原型允许模型生成自包含 HTML/CSS/JavaScript，用来测试声明式组件无法覆盖的真实上限。它必须同时满足：

- 独立临时数据仓与专用 WKWebView。
- 严格 CSP，禁止网络、iframe、弹窗、下载、存储和导航。
- 只允许 `ready / height / boundedAction` 三类桥消息。
- 节点、脚本、动画、时间、内存和高度都有硬预算。
- 失败时展示静态截图或文字，不让空白页留在回答中。

这条路线只有在双原型证明“额外自由确实带来明显学习增益”后才进入产品。

## 双原型要回答的唯一问题

不是比较哪张更漂亮，而是决定生成自由度的边界。

### 原型 A：自定义 OpenUI 学习库

- 使用 OpenUI 的语言、解析和 React 运行时。
- 不导入默认视觉库，只注册魏碑组件。
- 至少实现函数参数探索、对象/状态模拟、图像叠层三种实质不同的形态。
- 验证 Pi Prompt 是否能从同一组件定义自动生成。

### 原型 B：受限自包含 HTML

- 模型按魏碑设计规范和参考生成完整 HTML/CSS/JS。
- 在专用无网络宿主中运行同样三道题。
- 记录生成成功率、修复次数、视觉差异、互动正确性、性能和安全问题。

### 选择规则

| 结果 | 决策 |
| --- | --- |
| A 已能达到目标 | 声明式主路覆盖该能力，不开放自由代码 |
| B 明显更好且可稳定修复 | 为该类能力设计新的深组件，先吸收进 A |
| B 的优势无法被组件化 | 申请高自由度实验舱 |
| 两者都没有学习增益 | 回到纯文字或静态插图 |

因此 B 的价值主要是探索组件库尚缺什么，不是默认把任意网页交给用户。

## 与现有魏碑的最短接法

现有代码已经具备大部分宿主基础：

- 笔记编辑器已有本地 WebView、主题同步、双向桥、自动高度和外层滚动转发。
- HTML 阅读器已有字符串与本地文件加载。
- Agent 消息已经能嵌入自适应高度的 WebView。
- `RichAnswerSceneHost` 已经是原生与网页渲染器切换的正确接缝。

但不能直接复用现有 WebEditor 或 HTML 阅读器作为沙箱。新宿主要重新做：

- 非持久数据仓。
- 导航与新窗口全部拒绝。
- 网络内容规则与 CSP。
- 独立、最小化消息桥。
- 高度有限数检查与上限。
- 消息滚出懒加载区域后的状态恢复。

## 第一轮验收

双原型和后续产品实现共同使用以下门槛：

1. 真实 Pi 生成，不用硬编码最终答案替代端到端。
2. 数学、物理、化学、生物、文本、历史、图像设计、统计至少各有一题。
3. 至少三题的主要信息不能靠同一种线图表达。
4. 每题只有一个明确主互动，互动后知识结果必须真实同步。
5. 视觉统一但主要构图不能全部相同。
6. 正文内不强撑满屏；复杂内容能进入展开或聚焦面。
7. 关键结论、数据、区域或步骤可以回跳材料证据。
8. 深浅色、360pt、宽栏、设备像素比、键盘、减少动效、长回答和失败降级通过。
9. 任何空白、假按钮、静态假联动、原始协议暴露都算失败。
10. 验收不强制具体底层图元、组件名或逐题视觉答案；必须说明所选 T1/T2/专业渲染器为什么适合当前知识形状，不适合时诚实降级。

## 下一步

1. 保留已认可的 T1 深组件，继续把共性交互下沉为 T2 允许集合和注册渲染能力；不为每道题新写专属组件。
2. 让高复杂度 T2 逐步获得 Web 级视觉上限，但只在同一受控协议与透明内联宿主中演进，不回到任意整页 HTML。
3. 继续扩大 40+6+9+1 矩阵的真实模型分层抽验，优先查纯文本选择、图像素材绑定、冲突来源、渲染器适配和高风险降级。
4. 补齐深浅色、窄宽、设备像素比、键盘、减少动效、极长回答和更多不同视觉结构的真实窗口证据。
5. 完成学习有效性对照，再判断哪些组合值得固化为新深组件，哪些应保持开放组合。
