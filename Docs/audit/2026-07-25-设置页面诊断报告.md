## 0. 结论先行

设置页面最近 7 个提交（`5241c746` → `1f62d7e6`）是连续的"declutter / drop / hoist / fix"补丁序列，每一条都在修补上一次的表面问题，而**根因——信息架构本身——从未被触碰**：

- **总览 Tab 是一堆只读状态镜像**，和其它 Tab 重复，没有"设置"功能。
- **同一个控件跨 Tab 重复**（每日灵感出现 2 次且文案不一致；资料/笔记状态在 3 处重复）。
- **对话设置页（线性决策链）有多处真实 bug**：密钥隐式保存、模型列表并发 fetch 竞态、Profile 删除无确认、Anthropic OAuth 入口丢失。
- **内部 TODO 直接暴露给用户**（"待定稿 / TBD"）。
- **代码结构上**，`SettingsView` 是 `WeiBeiApp.swift`（AGENTS.md 共享核心文件）里的 833 行巨型 extension 宿主，任何对话设置改动都触发共享文件占用流程，导致每次微调都重。

下面的问题按**严重度**分级。每个问题给出证据位置（`文件:行号`，可点击）、根因、影响、修复建议方向。

## 一、严重（数据安全 / 功能错误）

### ~~S1. 密钥保存与 UI 严重脱节，存在隐性丢失风险~~（已修复）

**原证据（诊断时）**
- 密钥字段只靠 `onSubmit`（回车）和 `onChange(focusedField)`（失焦）落盘，切换 Tab / 关窗可能丢 key。
- `openAIKeyHelpText` 还写着"点「保存到钥匙串」"，但 UI 没有对应按钮。

**最终方案（第 3 轮收尾，2026-07-25）**
采用诊断里的**隐式自动保存**路径，而不是显式「保存」按钮（第 1 轮 PR #32 曾加过显式按钮，后与产品心智/自检契约对齐后撤回）：
- `AgentSettingsView`：在 `onSubmit` / 失焦之外，增加 `onChange(of: store.openAIAPIKey)`，输入即写入 Keychain。
- `WorkspaceStore.openAIKeyHelpText`：文案改为"自动写入当前配置的钥匙串"，与 UI 一致。
- 不保留显式「保存」按钮，避免双路径心智。

### S2. 模型列表并发 fetch 竞态（切换 Profile 会串列表）

**证据**
- `Sources/WeiBei/Views/Settings/AgentModelPicker.swift:14-18` —— `requestModelListRefresh()` 直接 `Task { await store.refreshModelList() }`，**无去重、无取消、无序列化**。
- `Sources/WeiBei/Views/Settings/AgentSettingsView.swift:22-32` —— `onAppear`、`onChange(agentProviderID)`、`onChange(activeAgentProfileID)` **三处都会触发** `requestModelListRefresh()`。
- `Sources/WeiBei/Stores/WorkspaceStore.swift:2913-2933` —— `selectAgentCredentialProfile` 切换时清空 `availableModels = []` / `modelListStatus = .idle`（L2930-2931），然后 UI 侧 onChange 再异步 fetch。
- `Sources/WeiBei/Stores/WorkspaceStore.swift:2832-2840` —— `refreshModelList` 是 `async`，多个并发调用各自走完网络请求后**覆盖** `availableModels` / `modelListStatus`，没有任何任务 ID / generation 校验。

**根因**
缺少"当前请求属于哪个 (provider, profile) 快照"的概念。最后一次写入胜出，而不是"对应当前状态的请求"胜出。

**影响**
快速操作（切到 A 再切到 B，或切 provider 的同时 onAppear 还没结束）会触发多个并发 fetch。若 A 的响应晚于 B 到达，**界面会显示 A 的模型列表而当前 provider 是 B**，且 `✓` 选中标记错位。这是最近 `1f62d7e6 fix(settings): clear stale model list on profile switch` 想修但没修干净的问题——清空旧列表只解决了"显示空"，没解决"并发覆盖"。

**修复方向**
- 在 Store 里维护一个单调递增的 fetch generation（或 `Task` 句柄），每次发请求前作废旧的；响应回来时若 generation 不匹配则丢弃。
- 或把 `requestModelListRefresh` 收敛到一个带 debounce 的 actor 方法，保证同一时刻只有一个 in-flight 请求。

### S3. 删除当前 Profile 无二次确认

**证据**
- `Sources/WeiBei/Views/Settings/AgentSettingsView.swift:150-154` —— 「删除当前配置」直接 `store.deleteActiveAgentCredentialProfile()`，无 `.confirmationDialog` / `Alert`。
- `Sources/WeiBei/Stores/WorkspaceStore.swift:2966-2975` —— `deleteActiveAgentCredentialProfile()` 会 `remove` Profile 并 `try? AgentCredentialProfileStore.deleteAPIKey(profileID:)`，**Keychain 密钥一起删除**，不可恢复。

**根因**
UI 设计假设低频操作 = 低风险，但删除是不可逆的密钥销毁。

**影响**
误点直接丢失整套凭证（provider + key + model + baseURL）。对一个 30+ 提供商、需要重新登录或重新粘贴 key 的场景，代价高。

**修复方向**
在调用 `deleteActiveAgentCredentialProfile()` 前加 `.confirmationDialog`，明确告知"将删除配置及其钥匙串中的密钥"。

### ~~S4. Anthropic / Copilot 等订阅型 provider 的 OAuth 入口丢失~~（经复核：非问题，已撤销）

> **订正（2026-07-25，合并验收阶段）**：本条最初判断有误，经与产品方确认后撤销，不作为问题处理。

**最初的错误判断**
原报告认为"subscription kind 的 provider 只显示 OAuth 块、丢失了 API Key 路径"，并建议"同时露出 OAuth + API Key 两套控件"。

**复核结论**
- Anthropic / Codex 的 `kind == .subscription`，`agentAuthRow` 对它们渲染 `agentSubscriptionAuth`（OAuth 登录），这是**符合预期**的行为——订阅型 provider 走 OAuth。
- 产品方确认：**重构前 OAuth 块与 API Key 块各自独立、分开摆放的布局就是对的**，不需要在同一 provider 下同时堆叠两套控件。用户若想用 API Key，应选择对应的 API 型 provider（如 "OpenAI API"、"Anthropic API"），而非订阅型。
- 帮助文案 `keyHelp` 里"Claude 订阅用 OAuth；或粘贴 API Key"的措辞虽略有歧义，但属于文案层面的小问题，不值得为此改动认证架构。
- **结论：S4 撤销。** 不改代码。曾经在 PR #33 尝试过"在 OAuth 块下补 API Key 块"的方案，已被产品方明确否定并 revert。

**给后续的提醒**
诊断静态代码时，"控件分支逻辑"与"产品意图"可能不一致；涉及认证/布局结构的判断必须与产品方确认后再定为"问题"。本条是反面教材。

## 二、中等（信息架构 / 文案 / 体验）

### ~~M1. "总览"Tab 是只读镜像，没有设置功能~~（已修复：第 3 轮删除总览，默认进入「对话」）

**证据**
`Sources/WeiBei/App/WeiBeiApp.swift:1499-1602`（`overviewSettings`）四个 group：
- 「连接状态」—— 只读 pill：提供商 / 密钥 / 模型（L1501-1528）。
- 「数据」—— 只读 pill：资料 / 笔记（L1530-1547），混入一个"每日灵感" toggle。
- 「快速进入」—— 三个跳转链接（L1565-1581）。
- 「关于」—— 版本 + 隐私占位（L1583-1600）。

其中**连接状态、数据状态在「对话」「资料与数据」Tab 里完整存在**，总览只是只读复述。「模型」行（L1522-1527）甚至 detail 和右侧 pill **显示同一个 `store.modelName`**，纯冗余。

**根因**
总览页被定位成"仪表盘"而非"设置入口"，但它的存在让用户多一层导航，且制造了与功能页的内容重复。

**影响**
- 用户打开设置第一眼是只读状态，不是可调项，违背"设置页用来改东西"的预期。
- 内容重复 → 改任何状态展示要改两处，容易不一致（S1 的文案问题就是这么来的）。

**修复方向**
二选一：
- 把总览改造成"快捷操作"集合（真正的高频设置 + 跳转），移除只读镜像。
- 或彻底删掉总览，默认进入「对话」或上次访问的 Tab。

### ~~M2. 同一控件跨 Tab 重复，且文案不一致~~（已修复：随总览删除去重，每日灵感仅外观一处）

**证据**
"每日灵感"（`showDailyInspiration`）出现两次：
- `WeiBeiApp.swift:1547-1562`（总览「数据」）—— 文案："关闭后**只隐藏语录**；文稿、对话和笔记入口始终保留。"
- `WeiBeiApp.swift:1648-1663`（外观「工作区」）—— 文案："只控制**空工作区里的出处内容**；文稿、对话和笔记入口始终保留。"

**同一开关，两处文案说法不同**，用户会怀疑这是不是两个不同的设置。

资料/笔记状态同样重复：
- 总览「数据」（L1530-1547）的资料、笔记行 = 「资料与数据」Tab（`dataSettings` L1844-1894）的资料、笔记行，**完全重复的只读 pill**。

**根因**
没有"单一来源"约束，控件随 Tab 需要被就地复制。

**影响**
文案分歧直接误导用户；控件状态若未来出现条件差异（如某 Tab 临时禁用），会造成"这里能改那里不能改"的诡异体验。

**修复方向**
每个设置项只在一个 Tab 出现。需要跨 Tab 提示时，用"跳转链接"而非重复控件。

### M3. 内部 TODO / 占位文案直接暴露给最终用户

**证据**
- `WeiBeiApp.swift:1585-1587` —— 「版本」detail："**正式法律文案与许可证在发布 closeout 前定稿**，此处只保留信息架构。"
- `WeiBeiApp.swift:1594-1599` —— 「隐私占位」标题就叫"**隐私占位**"，detail 写"最终隐私文案**待发布定稿**"，右侧 pill 是"**待定稿 / TBD**"。

**根因**
这些是给开发/PM 看的占位，被当成了用户可见文案。

**影响**
设置页出现 "TBD"、"待定稿"、"占位"、"closeout" 这类内部黑话，对终端用户非常不专业，削弱产品信任。

**修复方向**
要么写真实的版本号 + 真实隐私说明（哪怕一句"密钥仅存本机钥匙串"），要么暂时隐藏该行。绝不暴露 TODO。

### M4. 环境变量检测有两套独立实现，可能不一致

**证据**
- `Sources/WeiBei/Views/Settings/AgentSettingsView.swift:344-352` —— `envKeyOverride`：检查 `environmentAPIKeyName` 和 `OPENAI_API_KEY`。
- `Sources/WeiBei/Stores/WorkspaceStore.swift:1311-1323` —— `openAIKeyHelpText`：**独立实现**一遍环境变量检测，覆盖的变量和分支逻辑略有不同（含 fallback 到 `OPENAI_API_KEY` 的文案）。
- `Sources/WeiBei/Views/Settings/AgentModelPicker.swift:144-148` —— `envModelOverride`：**第三套**，检查 `WEIBEI_PI_MODEL` / `WEIBEI_OPENAI_MODEL`。

三处分别判断"环境变量是否生效"，互相不引用。

**根因**
环境变量真相分散在 UI 层多处，没有收敛到 Store 的单一计算属性。

**影响**
未来新增一个环境变量名，要记得改三处；漏改一处就会出现"UI 说已生效但 Store 没用"或反之。

**修复方向**
在 Store 暴露 `activeEnvOverride` / `envModelOverride` 两个计算属性，所有 UI 引用 Store 的值。

## 三、较轻（设计 / 代码结构 / 可维护性）

### ~~L1. 巨型文件 + extension 宿主，触发共享文件占用瓶颈~~（已修复：SettingsView 已迁出独立文件）

**证据**
- `Sources/WeiBei/App/WeiBeiApp.swift` 单文件 **2077 行**（其中 `SettingsView` 占 L1244–L2077，约 833 行）。
- AGENTS.md 把 `Sources/WeiBei/App/WeiBeiApp.swift` 列为**共享核心文件**："修改共享核心面之前，必须在任务对应的 issue 或草稿合并请求中写明占用……同一文件同一时间只能由一个活跃任务占用"。
- `AgentSettingsView.swift` / `AgentModelPicker.swift` 是 `SettingsView` 的 extension，逻辑跨 3 个文件。

**根因**
设置 UI 没有独立成文件，寄生在 App 入口文件里。

**影响**
- 任何对话设置的小调整都要占用 `WeiBeiApp.swift`，按 AGENTS.md 流程需要声明占用 + 等释放，**放大了每个改动的协调成本**——这正是最近 7 个补丁串联而非并行的结构性原因。
- extension 共享 `SettingsView` 的 `@State`（spinAngle / showManualModelEntry / isRenamingActiveProfile / profileRenameDraft，L1252-1256），跨 extension 共享可变状态在 SwiftUI 里是脆弱模式。

**修复方向**
把 `SettingsView` 及其基础原语（settingsGroup / settingsRow / settingsPill / compactMenu 等）抽到 `Sources/WeiBei/Views/Settings/SettingsView.swift`，从 `WeiBeiApp.swift` 移除。这样对话设置改动不再触碰共享核心面。

### L4. 固定 860×610 窗口，响应式差

**证据**
- `WeiBeiApp.swift:1265` —— `.frame(width: 860, height: 610)` 硬编码。
- 对话 Tab 在加了 Profile + Base URL + Region 后内容已接近临界，靠 `ScrollView`（L1414）兜底。

**根因**
固定尺寸换取排版稳定，但牺牲了可扩展性。

**影响**
未来增加设置项（如 Bedrock 的多 region、Vertex 的 project/location）会持续逼近窗口边界；小屏笔记本上 610 高度也偏紧。

**修复方向**
至少允许垂直方向自适应（min 610，可拉伸）；水平方向可保持固定。

### L5. Provider 链接与文案硬编码，无集中校验

**证据**
- `Sources/WeiBeiCore/AgentCredentialProfiles.swift:68-204` —— `AgentProviderConsoleLinks` 里 30+ provider 的 `loginURL` / `accountURL` / `keyHelp` 全部硬编码字符串，`switch` 覆盖所有 case。
- 双语 `language.text(中文, 英文)` 手写散落各处。

**根因**
为快速适配多 provider 而就地展开。

**影响**
新增 provider 要改多处 switch；URL 失效无运行期校验；双语维护成本高（每个文案两份）。

**修复方向**
非本次重点，但长期建议把 provider 元数据（label / url / env / default model / recommended models）收拢成一张数据表。

## 五、根因总结与修复路径建议

**根因**：设置页面的核心病灶不在任何一行代码，而在**信息架构**——"总览 = 只读镜像"的定位导致跨 Tab 重复，重复又导致文案分叉（S1、M2、M3）；为了消除重复带来的视觉噪音而做的"线性化重构"，引入了异步竞态（S2）。最近 7 个提交是在不触碰信息架构的前提下反复打补丁，每修一个表面问题就暴露一个新问题。（注：原报告把 S4 也算作重构引入的退化，经复核已撤销——重构后的 OAuth/API Key 分离布局符合产品意图。）
